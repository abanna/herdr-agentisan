# ADR-001 A52. A request the daemon took is never reported as not made

*Adds to:* A23 and A35. Recorded with NERD-5256, from #75's QA debt (N4) and #77's re-QA (N-1).

- **Why.** The CLI's daemon client mapped every failed exchange to `daemon_unavailable`: a dial that found no daemon, and an answer lost after the request was written. `docs/messaging.md` says to fall back to `herdr agent prompt` on that code, so a daemon killed between `send`'s commit and its answer had the message typed twice.
  - `Workforce` also asked a `not_ready` daemon again within one wait, the op's budget and an exchange.
  - A daemon that turned ready on a late ask ran the op on a budget of its own while the client's wait ended. The command then printed the earlier `not_ready`, and the natural answer, sending again, queued the message twice.
- **Sent or not.** `daemon.ErrNotSent` marks an exchange whose dial failed: the daemon ran nothing.
  - Every failure after the dial may have reached the daemon, so it is `ErrUnavailable` alone. A write that failed may have written part of the request, and the daemon reads a line closed without its newline.
  - This is the line herdr's client draws with its own `ErrNotSent`.
  - Both are `ErrUnavailable`, so the callers that ask only whether the daemon answered (back, the dashboard, the tab bar, `daemon health`) are unchanged.
- **The workforce commands' codes (A23).**
  - `daemon_unavailable` now means nothing was sent: no daemon took the dial, or the command found no socket. Its fallback advice stands.
  - A failure after the request was written is `daemon_no_answer`: the daemon took the request and gave no answer, so it may have run the op. Its doc row gives no fallback, and a queued message is delivered once the daemon runs again.
  - Every workforce op shares the rule, so a `worker retire` that ends so may have closed the pane.
- **The not_ready window (A35).** `Workforce` asks again for `NotReadyWindow`, 10 s, and the window bounds only the waits between asks.
  - Every ask, the window's last too, gets the op's whole budget and an exchange. So the client never abandons an ask that the daemon may still be running within its budget.
  - `not_ready` is returned only when the daemon answered it and no later ask reached the daemon.
  - An ask the daemon took and never answered within its whole wait is `daemon_no_answer`, after a refusal too.
  - No ask starts after the window, whichever way the wait before it ends.
  - A daemon that is never ready gets `not_ready` after about 10 s, where it got it after 15.
  - A command waits at most the window, the budget and an exchange: 25 s for `send` and `team status`, and 1,515 s for a retire after a handoff, under the skill's wrapper's 1,800.
- **What stays.** A deadline or a cancel of the caller's own that cuts short an ask after a `not_ready` still returns that refusal (A35). The CLI's only cancel is a SIGINT or a SIGTERM, so this is a caller choosing to stop, and the ask it cut short may have run.
