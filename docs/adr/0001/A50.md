# ADR-001 A50. Worker model routing: the rules and the deployment

*Adds to:* D9, D11 and A23. Recorded with NERD-5289 part 1a, from the user's routing rules v1 (2026-10-10) and the user's answers of 2026-10-21. Part 1a adds the domain package and its configuration; part 1b wires `worker spawn` to it (below); part 2 adds Jev's complexity answer for coders.

- **The rules are the spec.** The user's rules ship in the binary byte for byte (`internal/routing/rules/jev-routing-v1.json`), decoded strictly: an unknown key fails, so a rule from a later version is never silently ignored.
  - The plugin reads the bindings (a model id and the efforts it takes), and each role's allowed bindings, default (one, or one per provider), default effort and selection (`fixed`, `explicit` or `jev_complexity`).
  - It checks the rules against themselves: every default is allowed, runs under its provider and takes the role's effort.
  - A binding's provider is its name's prefix (`claude_`, `codex_`). A `*_premium` binding is never a default.
  - The role instructions in the rules (scope, the cleanup and output requirements, the pre-check skills, the findings requirements) stay in agentisan-skills (D9). The plugin reads past them.
- **The roles.** A worker type maps to a role:
  - coder: coder;
  - precheck: pre_check;
  - qa: pre_check (qa has no role of its own and verifies a handoff as pre_check does; the user's decision of 2026-10-20);
  - review: code_review;
  - research: researcher;
  - librarian: clerk;
  - debugger: alex_debugger;
  - boss: boss.
  - Any other type has no role, and is refused with `ErrUnknownRole`.
- **The provider is the type's agent command**, claude or codex (A23): the top-level command, `codex --no-daemon` for review, or a group's own command. A decision never changes it.
  - A packet preferring the other provider is refused, and so is an override naming one of its bindings.
  - A role with no default under the provider is blocked: the boss under codex, and code_review under claude. There is no fallback to the other provider (the user, 2026-10-22). The refusal names what the role allows instead: its bindings under the provider, as an override (`codex_strong` for the boss), or that it allows none there (code_review allows only `codex_strong`).
  - Putting a type on the other provider is a configuration change: its group's `agent.command`.
- **`[routing]`, the deployment.** The user's shared file and `--set` only, like `[telemetry]`. It is an unknown key in a project table and in a repo file, which whoever commits to the repo writes.
  - `enabled` (default false). While it is false, spawn launches as before and records the decision as what routing would have chosen (`applied: false`).
  - `[routing.bindings.<binding>]`: `model_id` (`""` marks it unresolved, never "the latest"), the `efforts` its client takes, and `enabled`.
  - `[routing.overrides] <role> = "<binding>"`: the user's standing choice, set in the shared file only, never `--set`, and the only way to a premium binding.
  - Binding and role names are the rules' own, so a misspelt one is an unknown key. An effort is one the binding's provider's client takes: low, medium, high, xhigh or max for claude (Claude Code's `--effort`), and minimal, low, medium, high or xhigh for codex (`model_reasoning_effort`). The rules' own bindings are held to the same lists.
  - While `enabled` is true, `config resolve` refuses every `agent.model` key, in any layer: routing sets the model.
  - This meets A46, which lets a repo file set `agent.model` and a group's: once routing is on, a committed repo file that sets a model fails `config resolve --project` and every workforce op for that project (`config_invalid`), until the key leaves the repo file.
  - `config resolve` shows each key with its layer, then the policy version (below) the resolved `[routing]` decides by: `routing policy: v1-…` in text, `routing_policy` in JSON.
- **The decision**, in order:
  1. The role and the provider are checked, then the boss's task packet, the rules' `task_packet`. Its `user_model_override` must be null: the user's override is theirs to set. Its size is bounded (part 1b, below).
  2. The binding is the user's override, else the boss's `--model` (a binding's name or its model id, never an alias), else the role's default for the provider.
     - The boss never picks a premium binding.
     - A `--model` other than the user's override is refused.
  3. The effort is the boss's `--effort`, else the role's default effort, else the binding's first.
  4. The hard filters with data apply: a model id, the binding enabled, and the effort supported.
     - An override that fails is refused (`ErrOverrideRefused`), never swapped for another binding.
     - A default that fails is `ErrBlocked`.
     - Part 2 adds the fallback from Jev's choice to the default.
- **The rules' filters with no data yet** (tool compatibility, context headroom, availability and spending limits) are listed in every decision as `unchecked`, until the user's activation defines them.
- **Jev's place.** A `jev_complexity` role (coder) takes its default with a reason, each logged apart, and no Jev call:
  - `task_not_found` (no packet, or not found);
  - `lookup_unavailable`;
  - `insufficient_assignment` (a blank assignment);
  - `jev_disabled` until part 2.
- **The audit record.** A decision carries every field the rules' `audit_fields` list, null or empty where it has nothing, plus `selection`, `applied` and `unchecked`.
  - The assignment is there only as `assignment_digest`: the sha256 of the assignment, the requirements and the acceptance criteria.
  - `policy_version` is the rules' schema version and a digest of the rules and the deployment, so a changed model id shows.
- **What a command may carry.** A23's launch flags gain `--effort`. A codex command is also refused a `-c`/`--config` that sets `model` or `model_reasoning_effort`, in any form clap takes. Before, `-c model=…` slipped past the `--model` check. Part 1b passes Claude its effort as `--effort`, and Codex its effort as `-c model_reasoning_effort="…"`.

## Part 1b: worker spawn asks routing

- **One decision per spawn.** Spawn asks routing after the preflight and outside the workforce lock, since part 2's Jev answer can take seconds, on the profile the preflight checked: one configuration read. Every worker of the spawn gets the same decision. A group missing from the profile, or one that only describes (A36), is still `unknown_group`, before routing is asked.
- **`team up` asks routing once per group it fills**, through the same path as spawn, with no task packet, `--model` or `--effort`. It asks under the workforce lock, on the configuration the lock read, and before any tab opens: a group routing refuses while it is on refuses the whole `team up`, the groups before it included, and nothing opens. Each group's decision is told and recorded as a spawn's is, with that group's workers.
- **One policy.** Spawn and `config resolve` make the policy of the same resolved `[routing]`, so a spawn's `policy_version` is the one `config resolve --project` prints.
- **While routing is on, the decision is the launch.**
  - Claude gets `--model <model id> --effort <effort>`, and Codex gets `--model <model id> -c model_reasoning_effort="<effort>"`.
  - If the type's command runs the other agent by the time the workers are planned, the spawn is refused (`config_invalid`): the configuration changed, so spawn again.
  - A spawn routing refuses opens nothing. The codes are `unknown_role`, `provider_mismatch`, `override_refused` and `routing_blocked`.
- **While it is off, spawn launches as part 4 does**, with `--model` and `--effort` passed as given.
  - The decision is made without them, as the role's own, and recorded with `applied: false`.
  - A spawn routing would refuse goes ahead, and the refusal is logged in `daemon.log`.
  - A malformed packet is a `bad_request` either way.
- **`--profile` is refused while routing is on.** A codex command that chooses a profile (`-p` or `--profile` in any form, or a `-c` that sets `profile`) fails `config resolve` and every workforce op while `enabled` is true, since a profile can set the model and effort routing decides. The plugin never edits Codex's config (A43). The error names the flag, never the profile.
- **`config resolve --project` checks each worker type against the user's overrides**, whether or not routing is on. An override whose binding runs under another provider than a type with its role is refused, naming both: `routing.overrides.pre_check: … claude_mid is a claude binding, and the worker type qa runs codex`.
  - Load leaves it there, so the project's other commands still run; a spawn of that type is refused (`provider_mismatch`), naming the type, since qa and precheck share pre_check.
- **The task packet** is `worker spawn --task-file <path|->`: one JSON object of the rules' `task_packet` keys and no other. Its bounds:
  - 512 bytes each for `task_id` and `title`;
  - 16 KiB each for `requirements`, `worker_assignment` and `previous_attempts`;
  - at most 64 items of 2 KiB each in `acceptance_criteria` and `required_tools`;
  - 64 KiB for all its text together, and for the file.
  - The daemon checks the bounds again on the request it receives.
  - It is UTF-8, in the file and in the spawn request the daemon receives. Other bytes are refused, since JSON would fold them into U+FFFD and the assignment's digest is of its bytes.
  - Spawn takes no `--set`: its request has fixed keys, so no spawn can re-map a binding's model id, say onto a premium one.
- **The worker's row records the decision it was launched with** (migration 0005): the role, provider, binding, model id and effort, the override (its binding, whose it was, and its effort), the assignment digest, the policy version and the time.
  - A worker routing did not launch records none.
  - Binding a retired or lost id writes its own decision over the old one, so a reused id never inherits a decision.
  - A handoff keeps the row, and with it the routing.
- **The audit.**
  - Each worker gets one `agentisan.worker.routed` event, with every audit field under `agentisan.routing.*` (`docs/telemetry.md`).
  - `daemon.log` gets one line per spawn with the whole decision. The decision never holds the assignment's text.
  - While routing is on, spawn's result names each worker's binding, model, effort and fallback reason.
