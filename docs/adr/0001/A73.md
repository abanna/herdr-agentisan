# ADR-001 A73. worker spawn's retry key

*Adds to:* D11, A1 (its retention, for two new tables), A23, A33, A35, A52 and A65, whose text is kept as written. Recorded with NERD-5254, from the user's decision of 2026-11-17: make `worker spawn` safe to retry and keep D11 as written, "Every command returns JSON and is idempotent on the logical ID, so the boss can retry safely". Built in parts, in this order, each adding its bullets here; a part may split into two pull requests:
- A, the store: this amendment's bullets so far;
- B, the store's writes, the code rule and the replay builder;
- C-read, the keyed op's read side: the keys in flight, the compare, replay and mismatch;
- C-write, the keyed fresh path;
- D, adopt and settle;
- E, the holds, `worker keys` and `worker resume`;
- F, the acknowledgement migration and `worker ack`, then the CLI's `--retry-key` and the socket accepting a key: the keys go live.

**Until C-read, nothing but the daily prune reads or writes the retry keys' tables,** and a spawn is answered as before.

- **Why.** A plain `worker spawn` takes the next free ids (A23), so a retry after an answer was lost would open a second set of workers. With a retry key, the same request retried returns its first answer and opens nothing more. That keeps D11's two promises: a retried spawn never starts a second worker, and the boss can always learn what a spawn did.
- **The key.** 32 lowercase hex characters, 16 random bytes, new for each request and the same on each of its retries. The boss's wrapper mints a new key for each spawn and keeps nothing; the daemon holds the record of every unfinished request. A person spawning by hand passes `openssl rand -hex 16`. It is not a secret. A key is **spent** once a worker row is bound under it. Before that, nothing was opened that a retry could duplicate, so a refused or dead attempt leaves it **free**.
- **The invariant (I-K).** Every answer the daemon gives for a key, after reading the key's record while holding the key, says its state: `free` (nothing was spawned under it), `open` (workers may exist: resume the key) or `spent` (the request is finished). Only the daemon writes a key state. A refusal the CLI made itself, a timeout, an answer that does not parse and a daemon refusal from before the read carry none. Every other report means: resume the key (`worker resume`), which never runs a request afresh. The boss leaves a request's key, by minting a new one or dropping the request, only on `spent` or `free`.
- **The storage.** The retry keys' migration (one-way, as every migration is, A1) adds two tables to `state.db`:
  - `spawn_requests`, one record per key: the request as it was asked (project, group, count, the model, effort and provider as passed, and the task packet's SHA-256, never its text, A50). A record is `running` until its answer is stored, then `done` with it: the code the daemon answered, and the refusal's message or the spawn's result as JSON.
  - `spawn_request_workers`, the ids the request planned, in order, written before the first tab opens, each with the generation it was bound at once it is bound.

  They are tables of their own, not a column on `workers`: a reused id rebinds its row (A35), and a column would lose the old binding. A link pins the id and its generation, so an answer can tell a worker retired since from one whose id was bound again.
- **Retention.** A record is kept 14 days from its first use, running or done, with its planned ids, as A1 keeps messages and handoffs. A running record with a bound row still `starting` is kept until that row is no longer starting, since a key forgotten while its workers come up would run afresh beside them. The daemon's daily prune deletes them, the only writer of the tables besides the spawn that holds a key.
- **The bind.** A worker a keyed spawn binds is bound and linked to its planned id in one transaction, through the same code as every bind, the worker checked before anything else, so a keyed row never exists without its link; no error repeats the worker's values. An answer is stored once, finished no earlier than its request began.
