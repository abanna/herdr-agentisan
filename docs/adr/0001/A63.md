# ADR-001 A63. Routing overrides per role and provider (Codex parity P17)

*Overrides:* A50's "an override naming one of its bindings is refused" (in "The provider is the type's agent command") and its "`config resolve --project` checks each worker type against the user's overrides" bullet. *Adds to:* A50. Recorded with NERD-5518, from the user's answer Q3 (Codex parity, 2026-10-23): overrides per provider. A50's text is kept as written. A62 (NERD-5517, P16) states the provider per worker type; this amendment is the overrides' part of it.

- **The shape.** `[routing.overrides] <role> = "<binding>"` or `<role> = ["<binding>", …]`, in the shared file only, never `--set` or a repo file, as before.
  - **A string binds only workers of its binding's provider.** The user's `coder = "claude_strong"` keeps Claude coders on Opus. A Codex coder decides as if the user had set no override: its default, `codex_strong` at high.
  - **A list sets one binding per provider**, such as `coder = ["claude_strong", "codex_strong"]`. Its order does not matter.
  - **Refused at load, naming the key:**
    - a list with two bindings of one provider, or one binding twice;
    - an empty list, which says nothing, so a typo shows rather than clears the override;
    - a binding the role does not allow, as before;
    - a value that is neither a string nor a list of strings.
  - A one-element list means exactly the string.
  - `config resolve` shows each override as written, with its layer.
- **The decision.** `choose` takes the user's binding for the worker's own provider (`Policy.UserOverride`); with none for it, the boss's `--model`, else the role's default.
  - The boss's `--model` is held to the user's binding for that provider alone: another binding of that provider is refused, and one of the other provider is `provider_mismatch`, as before. With no user binding for that provider, the boss may name any binding the role allows there; a premium one stays the user's alone.
  - A50's blocked pairs stand: the boss under codex has no default, so `boss = "codex_strong"` now binds Codex bosses and leaves Claude bosses on `claude_strong`, where before it refused every Claude boss.
  - The decision, the row and the routed event are unchanged: an applied override records its binding and whose it was. No migration.
- **The policy version.** A string is written into the version's digest exactly as before, so a deployment written before this amendment keeps its version: the live `coder = "claude_strong"` stays `v1-f0225362e568`. A list is written sorted, so its order is no fact of the version; a one-element list has the string's version.
- **`config resolve --project` checks each (type, provider) pair** the project's types run, whether or not routing is on. Load does not, so one type's override never stops the project's other commands.
  - An override can no longer name another provider than its workers', so A50's mismatch refusal goes.
  - It refuses a user override that every spawn of the pair would be refused for: a binding the deployment disables, leaves unresolved, or that does not take the role's effort. The refusal names the override, the type, the provider and why.
  - A role's default that fails is the spawn's to refuse (`routing_blocked`): it is not the user's override.
  - The pairs are each type's agent command's provider. P16 (A62) widens them to every provider a type may run, with no change to the check.
