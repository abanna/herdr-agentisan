# ADR-001 A33. Rotation: the context notices and the handoff token

*Amends:* D7's thresholds, which a role can now set for itself and which are crossed at their percentage; A46's repo-file keys, which gain a group's thresholds, read by the daemon; and A5's `handoff` row, whose writer is now the daemon. *Adds to:* A44, with a second source of notices; A23, with a command the daemon runs and retire's handoff guards; A35, whose store ends no row while its handoff is pending; and A21, with two events. Recorded with NERD-5261 (item 5b): part 1a of its PRs tells the boss about context levels, and part 1b makes the daemon the `handoff` token's writer (`handoff ready`). Part 2a adds retire's handoff guards, the read of the pending handoffs and herdr's split and rename calls, part 2b-1 the handoff's acknowledgement and the I2 gate, and part 2b-2 `worker spawn --replaces` and I5's test.

## Part 1a: the context notices

- **The thresholds.** There are three context percentages: soft, hard and the ceiling. The defaults are 55, 65 and 75.
  - `rotation.thresholds` is the project's. It applies to the boss and to every group without its own.
  - `groups.<type>.rotation.thresholds` is one role's, such as `qa`'s.
  - Either one is exactly three whole numbers from 1 to 100, strictly ascending. A bad one is `ErrInvalid`, and the error names its key path, such as `groups.qa.rotation.thresholds`.
  - A group that sets only thresholds still needs its `workers` and `slots`, or a description if it only describes, as a ◆ space does (A36).
- **A46 changes.** A repo file may now set a group's thresholds, as it already set the project's.
  - The daemon reads both when it starts, from the shared file, the project's table and the repo file; `--set` is only the CLI's. This is the first key the daemon reads from a repo file when it starts.
  - A threshold is a checked number, so at worst a committed file changes when the boss is told; it runs nothing and sends nothing anywhere.
  - Only the repo itself is resolved: no D12 check runs, so a repo without the Agentisan bundle still has its thresholds.
  - If a repo file can't be read, that's logged, and the project keeps what its other layers set. If the shared file doesn't resolve, that's logged too, and every team gets the defaults.
  - A change applies at the next daemon start, as A19's teams do.
- **Crossing.** A level is crossed at its threshold or above, so 55% is soft. The ctx display's bands (A28) start above 55 and 65, so at exactly 55% or 65% the boss is told a level while the sidebar still shows the band below. A28 is unchanged.
- **What is told.**
  - **Covered:** every agent pane a team places, the boss's included. The boss is told about its own context: `you are at 80% context (ceiling: 75%): hand off now; the user has been alerted`.
  - **Never covered:** a pane in no team, or a plain shell.
  - **Rises:** a rise is told once, at the highest level it newly crossed, so 40% to 78% is one notice, the ceiling's.
  - **Re-arming:** a level is told again only after it re-arms. A known ctx at its threshold less 5, or under, re-arms it and every level above it. So 75, 70, 75 tells the ceiling twice, and 75, 71, 75 tells it once.
  - **Unknown ctx:** a `ctx` that is absent, expired or not a whole percentage as its writer left it, or one on a pane herdr detects no agent in, whose `ctx` the model blanks (A27), tells nothing and re-arms nothing (D7).
- **The memory.** It is kept per terminal (A35), never per pane id.
  - A pane that moved keeps it.
  - A reissued pane id showing a new terminal starts fresh.
  - A terminal the model no longer holds is forgotten, so one that comes back is new.
  - A pane whose terminal herdr does not list is never told about.
  - The memory is not kept across a restart, so a restarted daemon tells each level a pane is past once more.
- **The lines.** Each names the worker as A44's do, with the item and stage it reported:
  - soft: `ha-coder-1 is at 56% context (soft: 55%) · NERD-5261 · verify: let it finish its unit, then rotate it`;
  - hard: `… (hard: 65%): rotate it now`. Part 2b adds the command, `worker spawn --replaces`, once it exists.
  - ceiling: `… (ceiling: 75%): act now; the user has been alerted`, or `the user's alert was not shown`.
  - The boss's own lines say "finish your unit, then hand off" for soft and "hand off now" for hard and the ceiling.
  - `notices.skip` can name `ctx_soft` and `ctx_hard`, never `ctx_ceiling` (A44). The levels are never dropped as repeats.
- **The ceiling alerts the user.** At the ceiling the daemon also shows a toast (`notification.show`): `agentisan: <worker> at <n>% context`, with herdr's request sound.
  - It is shown once per crossing, within one second, in the poll, before the boss's line.
  - It goes outside the Batcher, so the user sees it at once, while the boss's line can wait up to its `gap`.
  - A toast herdr does not show, and a call that fails, is logged and never tried again. The boss's line then says the alert was not shown.
  - It is the only herdr call the levels add to a poll.
- **Delivery.** It is A44's: `daemon.log` until G7 part 2 delivers through the inbox. Until then, "each level notifies the boss" is met by the boss following the log.
- **The event.** `agentisan.worker.ctx_level` records each crossing, with the worker, its level, ctx and threshold, and whether the toast was asked for and shown (`docs/telemetry.md`).

## Part 1b: the handoff token

- **The daemon is the writer.** A worker that has written its handoff runs `herdr-agentisan handoff ready`, and the daemon sets the `handoff` token on its agent pane. This closes A5's row: "the writer is `hready.sh` until worker rotation (item 5b) lands, then the daemon". `retire --after-handoff` reads the token as before.
- **What is written.**
  - The value is `⟳ READY TO RESTART`, the one `hready.sh` writes, so `$team`'s `⟳r` and the sidebar read either mark the same.
  - The source is `agentisan`, and the TTL is 24 h, herdr's longest. herdr keeps each key's TTL apart (`metadata_tokens.rs`), so `ctx`'s 180 s from the same source does not touch it.
  - `--clear` writes an empty value, which removes the token, with no TTL.
  - The token is written even when the pane already carries the value. herdr keeps one value per key, and the last write wins across sources, so the daemon's write replaces a mark `hready.sh` left and gives it the TTL.
- **Which pane.** Resolving the target never changes a `workers` row.
  - A live row's logical id names the pane herdr lists with the row's terminal (A35). A row bound to no pane, whether lost, with no terminal or with one herdr lists nowhere, is `unknown_worker`.
  - Otherwise a tabs team's worker tab label names its agent pane, and then a pane id names its pane, a stale one as `pane.process_info` resolves it.
  - With no target, it is the pane the command runs in, as its process lineage confirms it, unless herdr lists it with no terminal; else the pane of the live row `HERDR_AGENTISAN_WORKER` names, else `bad_request`.
  - The pane must be an agent pane in a team's group, in a tabs team or the ◆ spaces: one herdr detects an agent in, or knows one by name, as a held agent keeps its name. The boss's place, a shell and a pane in no team's group are `not_a_worker`. A boss hands off by its own protocol.
  - The command takes no `--project`: a logical id, a tab label and a pane id each name one pane on the server.
- **Proven before written.** The daemon writes only once `pane.get` shows the pane still has the terminal it read. A pane gone, showing another terminal or listed with none is `pane_changed`, and nothing is written. `retire --after-handoff` trusts the mark, so a mark on a reissued pane id would close the wrong worker.
- **The answer.** `{id, bound, project, group, pane_id, ready, changed}`, with the worker named as the team model names it: its logical id, or its pane id while no row binds it. `changed` is false when the pane already carried that value. Its other refusals are the codes every workforce op shares, such as `not_ready` (A35), `herdr_failed`, `config_invalid` and `store_failed`. The budget is 10 s, and the daemon's workforce lock serializes it with itself and with retire's close.
- **The event.** `agentisan.worker.handoff`, with step `ready` or `cleared`, records each mark the command changed; one that changed nothing records none (`docs/telemetry.md`). Part 2b adds the handoff's other steps.
- **The `hready.sh` cutover.** `hready.sh` wrote its mark with no TTL, so a mark it left never expires (Linear comment ae2380f6). The daemon never sweeps them on its own (D1). At the cutover:
  1. Workers stop running `hready.sh` and run `handoff ready` instead.
  2. The boss finds the marks left, from `$team`'s `⟳r` or `herdr pane list`.
  3. For each, `handoff ready <id>` adopts a mark still meant, with the TTL, and `handoff ready <id> --clear` removes one that is not.
- **Codex.** Under Codex's sandbox a tool command cannot reach the daemon's socket, so a sandboxed Codex worker cannot run `handoff ready`, and its boss marks it (A43).

## Part 2a: retire's handoff guards

- **The rule.** `worker retire` never ends a worker's row while its handoff is pending, on any path. That covers a logical id, a pane id, `--after-handoff`, a pane gone while retire waits, and a row bound to no pane.
  - It refuses `handoff_pending` before it closes anything, and names the replacement's pane.
  - The worker stays until the handoff completes (part 2b's acknowledgement) or fails. Retiring the replacement's pane fails it.
  - Without the rule, an ended row would strand the handoff. The handoff would hold the worker's inbox and block the id's next handoff until a spawn reused the id.
- **Where it holds.** The check runs twice.
  - Once when retire resolves its target, so `--after-handoff` is refused at once rather than after its wait.
  - Again under the daemon's workforce lock, from a fresh read of `state.db`, just before anything closes or ends. A handoff begins under that lock (part 2b's `--replaces`), so one begun while retire waited is seen.
  - Retire's resolving changes no row now: a row bound to no pane is ended under the lock too.
  - **A row rebound since retire read it** is `pane_changed`, with nothing closed or ended, and a retry reads it afresh. Under the lock, the row is read again too. The rebinding happened while retire waited: a handoff completed meanwhile, a new generation, or the team poll's re-key after a herdr live handoff (A35).
  - **Not covered yet: a herdr live handoff the poll has not re-keyed.** A live handoff renews the pane's terminal and keeps its pane id, and the poll re-keys the row up to 3 s later.
    - Until then retire finds the row's terminal listed nowhere and reads the pane as gone, whether during `--after-handoff`'s wait or at the close.
    - It then ends the row as `gone` while the worker still runs, as before this part. That is left for a follow-up.
- **The store's backstop.** `state.db` ends no row whose handoff is pending, whichever the ending (`retired`, `failed` or `gone`), as A35's `lost` already skips one. So no path, locked or not, strands a handoff.
  - A handoff begins only on a worker past `starting`. So spawn's `failed`, written outside the lock while its agent starts, never meets one. Part 2b refuses the rotation with `worker_starting`.
- **Abandoning a rotation.** Retiring a pending handoff's replacement pane fails that handoff, then closes the pane.
  - The worker keeps its row and its pane, and its inbox is released there. The answer names it: `handoff_failed: <id>`, beside the pane's `pane_id` and `outcome`.
  - Failing first means a close that errors leaves an ordinary pane, which a retry closes, and never an inbox held.
  - **Which pane is the replacement.** The pane herdr lists with the handoff's recorded terminal. Else the pane at its recorded pane id, while herdr lists that terminal nowhere: a herdr live handoff renews a terminal and keeps the pane id (A35). A reissued pane id whose recorded terminal herdr lists elsewhere is no replacement.
  - **A replacement herdr lists nowhere** (closed or crashed before the acknowledgement) is failed with nothing to close, as `outcome: gone`. Without this the worker could never be retired, and its inbox would stay held.
  - **D7's step 5.** After the acknowledgement no row is bound to the old pane, so `worker retire <old pane>` closes it, and the worker, now on the replacement, stays (part 2b).
- **herdr's calls for part 2b**, checked in herdr 0.9.5's source and added with no caller yet:
  - `pane.split` answers `pane_info` with the new pane's `terminal_id` (`src/app/api/panes.rs:133-140`), the terminal `BeginHandoff` records. It is never focused.
  - `agent.rename` with no name clears an agent's name (`src/app/agents.rs:98-101,130-133`).
    - Its target is an agent pane's id or an agent's name, never a terminal.
    - Renaming an agent to the name it has succeeds, so an acknowledgement can be run again.
    - A name is at most 32 characters of `[a-z][a-z0-9_-]*` (`agents.rs:15-20`), so a logical id takes `-next` only up to 27 characters.
    - `agent_launch_pending` has a sentinel of its own.

## Part 2b-1: the handoff acknowledgement

- **D7's step 3.** `herdr-agentisan handoff ack [<pane>]` (op `handoff.ack`) completes the pending handoff whose replacement the pane is. The pane is named by pane id, or with none it is the pane the command runs in.
  - The boss can name the pane, as can a hook, which is how a sandboxed Codex replacement acknowledges (A43). The replacement itself can also run it.
  - It never falls back to `HERDR_AGENTISAN_WORKER`, since the old pane and the replacement share it. With no pane named and none confirmed, the answer is `bad_request`.
  - The whole op runs under the daemon's workforce lock, the lock a handoff begins and a retire finishes under.
  - The replacement is found by part 2a's match (the recorded terminal, else the recorded pane id while that terminal is listed nowhere), shared with retire.
- **The replacement's agent.** The pane must host an agent herdr lists, or the answer is `not_a_worker`.
  - When a herdr live handoff has renewed its terminal, the pane id alone proves nothing. Its agent must still run under the replacement's herdr name `<id>-next`, or the worker's own name after a crash past the rename (herdr keeps names unique, and only the acknowledgement gives the replacement that name). Otherwise the answer is `handoff_changed`. The same code answers a replacement herdr lists nowhere. The boss then abandons it with `worker retire <pane>` and rotates again.
  - `pane.get` then reads the pane again. A pane showing another terminal is `pane_changed`, with nothing renamed.
- **I2's gate.** The replacement's `item` and `stage` come from that read, and both must be set.
  - They are compared with the old pane's only while the old pane reports both; `stage_at` is never compared. A difference is `stage_mismatch`, and the message names both pairs.
  - An old pane gone, or missing either key (a herdr live handoff erases every token), has nothing to compare. The acknowledgement then completes, and its answer and event say `old: unread`.
  - The daemon writes neither token (A6). To acknowledge, the new session re-reports the old pane's pair exactly (`herdr-agentisan report stage --item <item> --stage <stage>`), then runs `handoff ack` in the same turn, before its own `BOSS:`/`STATUS:` line rewrites the stage at the turn's end. The prompt hook reads only `item:`.
  - A Codex replacement in a sandbox, where neither command reaches the daemon (A43; under A59 a review, research or librarian one, or one whose command chose such a sandbox), ends its first turn with the old pane's `item:` line and status line, which its turn hooks report (A42). The boss then runs `handoff ack <pane>`.
- **The names move before the hold lifts.** The holder of the worker id's herdr name decides.
  - The old agent's name is cleared (`agent.rename` with no name).
  - The replacement is renamed to the worker's id.
  - Only then does `CompleteHandoffOnto` rebind the row and release the inbox, in one transaction (I3). It binds the new pane at the terminal it showed, and refuses one some live row binds already.
  - The dispatcher prompts only a bound pane whose agent has the worker's name, so no message reaches either session while the names move.
  - A replacement with the name already (a crash past the rename) renames nothing.
  - The name held by any other agent is `pane_changed`, with nothing renamed. A herdr live handoff the team poll has not re-keyed yet looks so too, and a retry after the poll's next pass completes.
  - A clear whose agent went meanwhile has nothing to clear. A rename that fails puts the old name back, best effort, and answers `herdr_failed`, with the handoff still pending: the acknowledgement can be run again.
- **The answer** is `{id, project, group, old_pane, new_pane, handoff_id, item, stage, old, changed}`. D7's step 5 is then `worker retire <old_pane>`.
  - An acknowledgement repeated after the handoff completed (a crash past the complete) answers `changed: false` and renames nothing. The pane must be the worker's bound pane, with its agent named the worker's id and a handoff completed onto it.
  - The old pane acknowledging by mistake, while the handoff is pending, is `no_handoff`, naming the replacement. So is any other pane.
- **Codes.** `no_handoff`, `handoff_changed` and `stage_mismatch` are new. `worker_starting` now answers a handoff begun on a worker still starting, as part 2a promised.
- **Telemetry.** The handoff event gains the steps `completed` (the acknowledgement) and `failed` (retire abandoning a rotation; part 2b-2's spawn failure too), with the pane the worker was on and, on `completed`, how the old pane read.
  - The workforce reports each step as it happens. A retire whose close fails after the handoff failed still reports it.
  - `acknowledged` is dropped: the acknowledgement completes in the same op. `begun` comes with part 2b-2's `--replaces`.
- **Startup** leaves a pending handoff alone: completing one without an acknowledgement would be the daemon acting alone (I5, part 2b-2's test).
- **Not covered yet:** retire abandoning a rotation after a partial acknowledgement (a crash between the clear and the complete) leaves the old agent with no name. The dispatcher cannot reach that agent until it is renamed. That is left for a follow-up.
