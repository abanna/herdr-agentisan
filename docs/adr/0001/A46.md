# ADR-001 A46. What a repo file may set

*Amends:* D9's precedence, whose repo file layer no longer sets every profile key, and D9's profile, whose models are now checked. *Adds to:* A23's configuration that `worker spawn` reads, and A36's "Never in a repo file". Recorded with NERD-5352: QA of #47 (NERD-5254 part 3) showed a committed repo file setting `shell_ready_keys`, and the user decided what a repo file may not set. Security QA of #64 then showed a model reaching a non-POSIX shell unchecked and a later key settable by default, and the boss chose the fixes below.

- **The keys.** A project's `.herdr-agentisan.toml` may set only `color`, `github`, a group's `workers` and `slots`, `agent.model`, a group's `agent.model`, and `rotation.thresholds`. Every other key, and every key the schema gains later until it is listed, comes only from the user's own layers: the shared file, its `[projects.<name>]` tables and `--set`. A test fails while a profile key is placed on neither side, so a new key's side is chosen where it is reviewed.
- **Why.** A repo file is committed, so whoever can commit to the repo writes it. Every workforce op resolves the project's profile with it (A23), unlike the team poll, which reads no repo file (A36).
  - A command, `agent.command` or a group's, would run in a new tab of the user's terminal.
  - `[spawn]`'s `shell_ready_keys` would be typed into whatever program holds that tab, and `shell_prompt` and `shell_ready_after_s` decide when.
  - `verify` is commands to run.
  - An integration's `token` and `url` together decide which of the user's secrets is read, and where it is sent. `config resolve --check-secrets` already runs `op read` on the reference.
  - A key the daemon reads only from the shared file, such as a description (A36), would show in `config resolve` and do nothing.
- **Models stay, checked whichever layer sets them.** A model is a letter or digit, then letters, digits and `. _ - : / @ [ ]`, at most 128 bytes: `opus[1m]`, `gpt-5.1-codex`, a Bedrock id ending `:0` and a Vertex one with its `@date` all pass. Anything else is `ErrInvalid`, set in the shared file, a project's table, the repo file or `--set`. The model checked is the merged one, the one an agent gets: a layer's model that a higher layer overrides is never passed, and not checked. The workforce passes a model as one argument after `--model`, and herdr's `agent.start` (herdr 0.9.5) types it into the pane's shell bare when every character is in herdr's own safe set (letters, digits and `@ % _ + = : , . / -`), and otherwise inside single quotes: PowerShell's for pwsh, POSIX ones for every other shell. fish, which herdr also accepts, reads `\'` inside POSIX single quotes as an escape, so a quote or a backslash could end the quoting and run a command. None of the allowed characters is special in either form in any shell herdr accepts, and the first can never start a flag. The check refuses a live config's model as surely as a repo's, and, like every other field check, one project's bad model fails the project-less load the daemon's team poll reads; the shared file set none when it landed.
- **Set means present.** A key is refused whatever its value, an empty list or `""` included. A higher layer replaces a lower one's value whole, so a repo file's `shell_ready_keys = []` or `verify = []` would still undo the user's own. A table that sets no leaf, such as an empty `[spawn]`, passes. A table, an inline table and a dotted key name the same key.
- **The error.** `ErrInvalid`, naming the key, the layer and its file, and for a repo file's key where to set it instead (`herdr-agentisan.toml` or `--set`). It never names the value, and the first such key in path order is the one reported.
  - A workforce op answers it `config_invalid`.
  - A plain secret in a repo file is still `ErrSecretValue`, first, as in every layer.
  - A repo file that sets another key now fails `config resolve --project` and every workforce op for its project until the key moves to the shared file.
