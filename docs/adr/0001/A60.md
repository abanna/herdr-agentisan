# ADR-001 A60. The team board: workers post, only the boss and the user read

*Adds to:* D1, D8, A1, A2, A18 (the snapshot), A23, A30 and A44. Recorded with NERD-5533, the user's design of 2026-10-23, in parts:
- 1a A, the board and its readers: this amendment's bullets so far;
- 1a B, the writes: notices, `send` to a boss and each turn's `BOSS:` line become posts, and nothing is typed into a boss again;
- 1b, the user's view: the dashboard's board panel, `board.seen`, which moves the user's mark to what it showed, and the snapshot's unread count with its badges;
- 2, a message typed into a worker held while its input box holds text (NERD-5527);
- 3, a Codex boss's wake.

Each part adds its bullets here. **Until 1a B, nothing writes to the board:** delivery to a boss is still typed, as A30 and A44 say.

- **The board.** Each team's board is its posts in `state.db` (`board_posts`, migration 0007), in one of two channels: `team`, what its workers, panes and bosses post, and `daemon`, the daemon's notices. Only the team's boss and the user read it. Workers only write to it: no worker reads a post, its own included, and there is no worker-to-worker chat on it.
  - **A post** has its project, channel, author (a worker, a boss, a pane by its terminal, or the daemon), kind (`post` on the team channel, a notice's kind on the daemon's), the pane or PR it is about and the worker it names, for a notice, its body and its time. Its body is checked as a message's (at most 8 KiB of UTF-8 with no NUL), and every other field as an id.
  - **Its seq** orders a project's posts and is never handed out twice, even after every post was pruned (`AUTOINCREMENT`), so a read mark never hides a new post.
  - **Retention:** 30 days, and at most 2,000 posts a project, the oldest first; pruned at start and every `PruneInterval` (a day), beside the messages, so a board can run past either cap by a day's posts.
  - **One write path.** Every post goes through the store's one write connection, which wakes every `board wait` at each post, whichever writer made it.
- **Two read marks** a project (`board_marks`): the boss's and the user's. A read moves only its reader's, so the boss reading never clears the user's badge. A mark only moves forward, past the posts read.
- **The readers' ops.** The daemon serves the board only through these ops, each placing its caller first:
  - `board.read {limit, all}`, budget 10 s: the caller's unread posts, oldest first, at most `limit` (50 by default, 200 at most), its mark moved past them in the same transaction, with how many are left; or, with `all`, the newest posts, newest first, moving no mark, as the panel reads.
  - `board.wait {after, timeout}`: it answers once the newest post is past `after`, which is the caller's mark when not given, so a post made between a read and the next wait is never missed; at once if one is there already. Otherwise it waits for a post, its timeout (30 min by default, 6 h at most; its budget is the timeout and an exchange) or the daemon's stop (`daemon_gone`). It answers counts only, never a post. One wait a pane: a later one from the same pane ends the earlier (`superseded`), so restarted waits never stack.
- **Who reads: placed by the kernel, not by the request.** Each op takes its caller from the connection's peer credentials (`SO_PEERCRED`, `LOCAL_PEERPID` on darwin), never from a field the client writes. The caller's process ancestry (`report.ReadLineage`, with no anchor, since an anchor would come from the caller's own environment) is matched against herdr's `pane.process_info`, asked at op time:
  - in a pane of its team's boss place, it reads that team's board as the boss. For a tabs team that place is the boss's tab, every pane of it but the dashboard's split, as the team model builds it: another program there, such as the team feed, a shell split into the tab, or the old boss during a handoff, reads as the boss too. Each is the boss's or the user's: every worker has a tab of its own, and a split in the boss's tab is the user's or the boss's own act. Checking the boss's agent name instead would lock a new boss out after a handoff until the poll names it;
  - in a pane of that boss place, or of the boss's tab, whose foreground runs the plugin's dashboard (`herdr-agentisan dashboard`), as the user: a ◆ boss space holds its dashboard among the boss's panes;
  - anything else is `not_allowed`: a worker's pane, a dashboard in a worker's tab, the dashboard's split running anything but the dashboard, an orphaned process, another uid, a caller the kernel tells nothing of (any OS but Linux and darwin), and the check fails closed. A herdr call that fails is `herdr_failed`, not a refusal of the caller.
- **The CLI.** `herdr-agentisan board read [--all] [--limit N]` and `board wait [--after SEQ] [--timeout D]`, with A23's output: one JSON object, exit 1 when refused. `board wait` exits 3 when its timeout passes with no post, to be started again. The boss runs it as a background command and reads the board when it ends.
- **Policy, not a boundary.** Workers run as the user's uid, so a worker that opens `state.db` itself, reads the boss's or the dashboard's screen through herdr, or opens a pane in the boss's tab, where any program reads as the boss, is not stopped. The rule holds for every agent that goes through the plugin's commands; a boundary would need the daemon under a separate uid, or the workers sandboxed away from the plugin's state directory, which this does not add. Each worker's deny rules for the state directory, and its role's instructions, raise the bar without closing it.

- **The user's panel (1b).** `b` opens or closes the board from the overview or
  a group's view, returning to that view. The header stays; the posts replace
  the agents. Newest first, at most 200, each row shows a dot, time, channel,
  who (worker, then subject, then author), kind and the first body line. Enter
  expands the selected body in its column; arrows move between posts, or scroll
  by line within an expansion. PageUp/PageDown scroll by page and Home/End
  reach the expanded body’s beginning/end. `t` and `d`
  toggle team-only and daemon-only; pressing the same filter again shows both.
  Escape closes help first, then an expansion, then the panel. `◀ back` closes
  the panel. Search takes these letters as query text; a board never focuses
  an agent, and digits and `/` do nothing there.
  - One flight: read on open, mark after the answer, then read after 3 s while
    open, with a 5 s timeout on each operation. Closing schedules no more work;
    stale replies cannot update a later opening. Unavailable reads retain the
    last posts, with an error; `not_ready` waits and `not_allowed` explains
    the placement rule. No posts are drawn on either placement refusal.
  - `board.seen {upto}`, budget 10 s, uses the same placement as the other
    ops. It advances only the caller's mark, never backwards or past newest.
    The panel marks the newest post under its filter after a successful read.
    With `t` on, the mark moves past older hidden daemon posts; newer hidden
    daemon posts remain unread. Dots use the first read's mark until close.
  - The snapshot's optional `project.board_unread` counts the user's unread
    posts, never carrying post text, and is omitted at zero. `board N` leads
    the tab-bar line and sits before `[ btop ]` in the header. It gives way
    after the PR detail and btop button as width shrinks.
  - `--board-fixture` requires `--fixture`; `docs/dashboard/sample-board.json`
    previews both channels without a daemon. Its mark lives only in memory,
    and the fixture snapshot's badge follows it. The user's board preview
    before live activation remains mandatory; this slice installs nothing.
