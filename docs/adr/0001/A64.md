# ADR-001 A64. A caller under Codex counts only from its pane's own Codex

*Refines:* A30's sender and refusals, A33's `handoff ready` with no target, and A23's selector, the team a command means without `--project`. *Builds on:* A22 and A25. Recorded with NERD-5506 (Codex parity R39).

- **The problem.** Under Codex's shared app-server, a session's tool commands and hooks inherit the environment of the session that started the daemon: its `HERDR_PANE_ID` and its `HERDR_AGENTISAN_WORKER` (A22).
  - While that TUI lives, the command's parent walk runs through the app-server, that TUI and its pane. So the lineage check that confirms a caller's pane confirms the starting session's pane.
  - Once that TUI exits, no pane is confirmed, and the inherited `HERDR_AGENTISAN_WORKER` named the same worker.
  - So a hand-started Codex on the shared app-server could `send` as another worker, mark it ready with `handoff ready`, which `worker retire --after-handoff` would close, or run a team op on its team.
  - Spawned workers are not affected: spawn starts every Codex with `--no-daemon` (A22, A23).
- **The rule.** Before a command takes its pane or its `HERDR_AGENTISAN_WORKER` for its own, and before it asks herdr, one run under Codex must be run by its pane's own Codex.
  - A command runs under Codex when it carries `CODEX_THREAD_ID`, which Codex sets on every tool command, or when one of its parents whose arguments can be read runs Codex or an app-server. That is how a hook, which carries no thread id, is caught.
  - Such a command must pass `report`'s `CheckCodexHost` over its parents (A25): no app-server among them, and Codex itself.
  - The command's own process is left out of both checks. Its arguments are its caller's words: `send boss app-server` runs no app-server. A parent wrapper such as `timeout` whose arguments include `app-server` is refused, an accepted edge.
  - A parent whose arguments cannot be read does not make a command count as run under Codex. So Claude, or a shell, is never refused for an ancestor another user owns, which macOS's `procargs2` will not read.
  - Once a command counts as run under Codex, an unreadable parent fails the check, as for a report.
  - Codex's network sandbox is not refused, unlike for `report stage` (A25). It says nothing about which process runs the command, and an escalation Codex approved still carries it.
- **What fails it.**
  - `send`, and `handoff ready` with no target, are refused `caller_unverified`. They print one JSON object, exit 1, and never ask the daemon. The message names the cause and says to start Codex with `--no-daemon` and run the command outside its sandbox.
  - A sandboxed command's walk ends inside Codex's pid namespace, with no Codex in it. So an unescalated `send` from Codex's sandbox is now refused `caller_unverified`, no longer at the connect.
  - Under Codex on an OS with no process table reader (neither Linux nor macOS), the check cannot pass, so the command is refused, as `report stage` is (A25).
  - The team ops (A23) treat such a caller as one in no pane they can confirm. They take `--project`, else the only tabs team, else they refuse `bad_request`. The starting session's pane never chooses the team, though the only tabs team may be that session's.
- **What is unchanged.**
  - Claude, a shell, and the pane's own Codex (`--no-daemon`) find their pane and their `HERDR_AGENTISAN_WORKER` as before.
  - The daemon still takes the caller the command names: there is still no authentication (A30).
  - Placing the caller by the socket's peer credentials, as the board's ops do (A60), would move this check into the daemon. That is a later change.
