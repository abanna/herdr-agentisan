# ADR-001 A55. The Codex review worker's role

*Refines:* D9's "Canonical role instructions stay in agentisan-skills", as A32 did for the debugger, and A43's "The workforce adds no sandbox flag", for the review type's built-in command only. Recorded with G6, part of NERD-5278, from the user's decisions of 2026-10-22 and the boss's answers to its questions.

- **Codex review is two things:** the GitHub Codex connector on PRs, and a team `review` worker.
  - The connector stays off until onboarding a new project works, so nothing here depends on it.
  - Adding `## Review guidelines` to this repo's `AGENTS.md`, which the connector reads, waits until then. Every Claude and Codex session here reads that file, and the section's "report only findings meeting P0 or P1" would sit against the coding workflow's P2 and P3 handling and QA's notes.
- **The reviewer is read-only.**
  - The boss prepares a worktree at the PR's head and names it.
  - The reviewer answers in its final message, ending on a `BOSS:` line, and the boss writes its findings to `team/qa-PR-<n>-codex-review.md`.
  - It never edits a file, never writes with git or gh, never reads the change from the checkout it started in, and never reacts or comments on GitHub.
- **The role is `roles/review.md`, shipped with the plugin.**
  - It vendors agentisan-skills' `## Review guidelines` byte for byte: `AGENTS.md` at c3dfe596 (2026-09-26), from that heading through the line before the next level-two heading.
  - That section says it is the canonical policy for hosted and local reviewers, and that a reviewer's brief includes it verbatim, with no conflicting scope, evidence or severity instruction. go-review's `review-policy.md` holds the same text.
  - A source note above it names the commit and the awk command that re-vendors it. The plugin works without Agentisan (A32), so nothing reads agentisan-skills at test or run time.
  - Around it, the role adds only how the reviewer works: its inputs, the read-only rules, the report's fields and its final line. It adds no scope, evidence or severity rule.
- **Each finding's fields:**
  - the guidelines' severity, P0 or P1, and their `[PRE-EXISTING]` label;
  - routing's `code_review` `findings_require`: concrete failure scenario, code references, existing safeguards checked, and evidence supporting severity.

  These map onto the guidelines' "Evidence required". "Existing safeguards checked" is a field the guidelines do not forbid.
- **The final line** is one of three:
  - `BOSS: review #<n> at <sha7>: no findings`;
  - `BOSS: review #<n> at <sha7>: <k> findings (P0 <a>, P1 <b>)`;
  - `BOSS: blocked: review #<n>: <reason>`, when an input is missing, the worktree cannot be read, its HEAD is not the head, or the base does not resolve.

  `report turn` (A42) reads it as the reviewer's stage. Before its inputs arrive, the reviewer answers `STATUS: waiting for a review`.
- **Delivery: two messages per review.**
  - Codex has no flag that appends a file to its instructions. `developer_instructions` is an inline string only, and `model_instructions_file` replaces Codex's base prompt rather than adding to it. Spawn sends no first prompt, and one would be lost at `/clear`.
  - So the boss sends:
    1. the role, whole: `herdr-agentisan send <id> - < roles/review.md`, within `send`'s 8 KiB;
    2. the inputs only: a first line, such as `Review inputs:`, then an `item: PR-<n>` line, then `pr`, `head`, `base` and `worktree`, one per line.
  - The item goes on the second line. The daemon types a message as `[msg <id> from <sender>] <body>` (A30), and `report turn` reads only a line that opens with `item:` (A42), so an item on the body's first line is never read.
  - Every review resends the role, so it survives `/clear` and rotation, at about 2k tokens of the reviewer's context each time. A pointer to the file would not do: a reviewer cannot apply a policy it was only pointed at.
- **No hints.** A review dispatch carries only those inputs: no scope, focus, evidence or severity hint, such as "look at X" or "this is minor". The guidelines forbid conflicting instructions in a reviewer's brief, and the dispatch is part of it. The role tells the reviewer that such words never change the guidelines.
- **The review type runs read-only by default.** Its built-in command is `codex --no-daemon --sandbox read-only`, so the role's premise holds with no configuration.
  - A group's own `agent.command` still replaces it (A23).
  - Nothing in the workforce reads `--sandbox`, so A43's `danger-full-access` opt-in for other groups is unchanged.
  - Under the read-only sandbox, the reviewer's ctx and turn hooks still run, outside the sandbox (A43). It cannot reach the daemon's socket to `send`, so the boss reads its final message.
- **Tests keep it in step.**
  - `internal/settings/reviewrole_test.go` pins:
    - the section's SHA-256, and the commit in the source note;
    - the role's guards;
    - its status lines, as `report turn` reads them;
    - the read-only default, and the role's statement of it;
    - that the role is a body `send` takes, and states no item as a prompt. That test logs the role's size and the bytes left under `send`'s 8 KiB (`go test -v -run TestReviewRoleFitsOneMessage ./internal/settings/`), and its failure says how far over it is.
    - the role's own text, everything around the section with the source note's commit and date masked, by its SHA-256 (NERD-5495, from #107's QA). Any edit to it, a rule in words no test knows included, sets a new hash, and whoever sets it re-reads the role for a scope, evidence or severity rule first. A re-vendor changes neither the text nor its hash.
    - that, outside the section, no severity label and no scope, evidence or severity word appears beyond the role's own sentences. So a rule added with a hash set but no re-read still fails.
  - `internal/routing/reviewrole_test.go` decodes the rules file and requires each of the review type's `findings_require` in the role's report section, since Go reads past that key.
  - An edit to the copy fails. An upstream change is caught only by re-vendoring, which the boss does when agentisan-skills changes the section.
  - Nothing detects that drift automatically: the plugin works without agentisan-skills, so no test or CI step reads it (NERD-5495 declined it). To check by hand, run `git log c3dfe596..HEAD -- AGENTS.md` in agentisan-skills; any output means the section may have changed.
- **Later:** `herdr-agentisan review brief --pr … --head … --base … --worktree …` could print the role and the inputs as one body.
  - The role would be embedded in the binary through a root-level `roles` package, since `internal/` cannot embed `../roles`.
  - It is worth its 150 or so lines if the two-message dispatch proves error-prone.
