# ADR-001 A59. Codex workers start in their type's sandbox

*Overrides:* A43's "The sandbox is Codex's own setting. The workforce adds no sandbox flag", for the coder, qa, precheck and review types, and A55's "Nothing in the workforce reads `--sandbox`". *Refines:* A55's "The review type runs read-only by default", which now covers a review command that chooses no sandbox too. Recorded with NERD-5516 (Codex parity P14, rows R1 and R18), from the user's decision Q1 (i) of 2026-10-23 and the boss's answers to its questions. A43's and A55's text is kept as written.

- **Why.** Under Codex's default for a trusted folder, `workspace-write`, a worker's tool commands cannot open sockets and `.git` stays read-only. So a Codex coder or qa cannot pass the repo's tests (`go test ./...` dials herdrtest's and the daemon's unix sockets), run `task check`, sign, push, run `gh` or the herdr CLIs, add a worktree, commit, or write a team file. Claude workers run with no OS sandbox. Q1 (i) gives Codex coder, qa and precheck workers the same reach.
- **The rule.** `settings.SandboxFor` maps a worker type to the sandbox its Codex starts in:
  - review: `read-only`;
  - coder, qa and precheck: `danger-full-access`;
  - every other type (research, librarian): none, so Codex's own configuration decides. The debugger is Claude's (A32).

  Spawn adds `--sandbox <mode>` to a codex launch right after `--no-daemon` (A22) and before the model and effort routing sets (A50). It adds it only when the command chooses no sandbox itself (`settings.ChoosesSandbox`). A Claude launch never gets it.
- **The user's choice stands.** A command chooses its sandbox with `-s` or `--sandbox` in any form, `--approve-for-me` or `--dangerously-bypass-approvals-and-sandbox` (or their hidden aliases `--not-so-yolo` and `--yolo`), or a `-c`/`--config` setting `sandbox_mode` or `default_permissions` (a permissions profile), as Codex 0.163.0 takes them (`utils/cli/src/shared_options.rs:38-59`, `config/src/config_toml.rs:223-243`). Adding `--sandbox` to any of these would break the choice: `--approve-for-me` conflicts with it, so Codex would refuse to start, and it would silently override either key. Spawn then adds nothing, and none of those flags is refused: they fight neither the workforce nor routing, as the user decided on 2026-10-23.
  - The override lives in the user's layers, in a group's or `[agent]`'s command. A repo file sets no command (A46), so a repo can neither loosen nor tighten a worker's sandbox.
  - There is no `sandbox` key. The command already says it.
- **Codex's own configuration is outranked.** A `sandbox_mode` or `default_permissions` in `config.toml` or a `-p` profile loses to the flag spawn adds, by Codex's own precedence (a `--sandbox` override selects the legacy sandbox before any profile, `core/src/config/mod.rs:2627-2634`), since spawn cannot read either. To run a type in another sandbox, the user writes it into the command. The sample and the README say so.
- **Review.** The built-in command keeps its own `--sandbox read-only` (A55), so spawn adds nothing to it and the flag appears once. A review group's own command that chooses no sandbox now starts read-only too, so A55's premise holds for any review command.
- **What full access costs and restores.** No OS sandbox and no reviewer, since `auto_review` sees only escalations, which `danger-full-access` never makes (A43's opt-in, now the default for these three types).
  - **It restores** the tests, git, signing, `gh`, the team's files and the handoff file under `.git/agentisan/` (row A13), and every pipeline `report stage` step (A25, row B6).
  - **It adds no approval flag:** with no sandbox there is no escalation to approve.
- **Per worker.** The sandbox goes with each codex launch, so in a group whose workers run different agents, each Codex worker gets its type's sandbox and each Claude worker none.
