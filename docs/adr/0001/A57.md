# ADR-001 A57. Jev's complexity answer for coders (routing part 2)

*Adds to:* A50. Recorded with NERD-5289 part 2, in four PRs:
- 2a, Jev in the domain: this amendment's first bullets;
- 2b-i, the switch and the key;
- 2b-ii, spawn's call;
- 2d, the calibration;
- 2c, the limit and headroom filters.

Each PR adds its bullets here. 2b-ii gives what 2a and 2b-i add its caller, `worker spawn`, as part 1b gave A50's routing its caller.

- **Two steps around a call routing never makes.**
  - `Resolve` decides as A50 says. A decision that should ask Jev says so (`AsksJev`), and its reason stays `jev_disabled` until an answer is applied. That is a decision:
    - of a `jev_complexity` role (the coder);
    - with no binding an override named;
    - whose packet holds an assignment (A50's reasons otherwise);
    - whose binding escalating could change.
  - The caller sends `JevRequest`'s body to TypeSafe, within `JevTimeout`, and hands `ApplyJev` the answer or the failure.
  - Routing never sees the key and makes no call.
- **The request** is the rules' `jev_request_template` exactly: its model (`jev-1.13.0`) and its two questions as given. The state is filled in from the packet:
  - `worker_assignment`;
  - `requirements`;
  - `acceptance_criteria` (`[]` for none);
  - `attempt_evidence`, which is the packet's `previous_attempts`.

  A packet that is not UTF-8 is refused, so no byte of it is silently replaced. Rules are refused as a whole when their template asks other questions or fills other state, or when their policy lacks either threshold, a `jev_timeout_ms` of 1 to 60,000, or a `jev_retries` of 0.
- **The client** is `internal/jev`. It makes one POST to System One, with the key as the Bearer token, within the rules' 2,000 ms. It never retries. It never follows a redirect, whatever HTTP client its caller gives it, so the key stays where it was sent.
  - Each of these is a failure:
    - a status other than 200;
    - an answer that is cut off, over 64 KiB, or lacks a model or answers;
    - no answer at all.
  - No error carries the key, the request or TypeSafe's body, which a 422 echoes.
- **The mapping**, for a decision that asks Jev, in this order:
  - **`jev_failure`, with `jev_error` (at most 200 bytes):** the default is kept. Any one of these causes it:
    - a failure;
    - a model other than the template's. TypeSafe's docs show the request's model echoed back; the first live answer, at calibration, confirms it for `jev-1.13.0`;
    - answers other than the two questions'. Those are a choice of bounded, demanding or unknown, with a confidence, and a noul, each from 0 to 1.
  - **`jev_insufficient`:** `information_sufficient` is below the sufficiency threshold (0.8).
  - **`jev_unknown`:** the complexity is unknown.
  - **`jev_low_confidence`:** the confidence is below the confidence threshold (0.75). A low confidence never escalates.
  - **bounded:** the default, with no reason.
  - **demanding:** the provider's strong binding at high (the rules' `complexity_mapping`), or at the boss's `--effort`. If a filter drops that binding, the default is kept with `escalation_ineligible`, as the rules' `ineligible_selection` says.

  A threshold met exactly escalates.
- **No call the rules make pointless** (the boss, 2026-10-22). A codex coder's default is already `codex_strong` at high, so its decision does not ask Jev: `jev_no_change`. The same holds for a coder whose role allows no strong binding under its provider. Asking would cost up to 2 s and a billed request, for nothing.
  - A deployment that only switches the strong binding off, leaves it unresolved, or drops `high` from it still asks. Then a demanding answer keeps the default as `escalation_ineligible`, with Jev's answers recorded, so the audit shows what the switch held back.
- **The audit.** A decision gains `jev_error`. Once Jev has answered, it fills `jev_model_returned` and `answers`: the two answers as read, with only their known fields.
- **The switch (2b-i).** `[routing.jev]` belongs to the shared file and `--set`, never to a repo file or a project's table: `enabled` (default false), `env_file`, and `confidence_pct` and `sufficiency_pct`.
  - A spawn asks Jev only while `routing.enabled` and `routing.jev.enabled` are both true (`Policy.JevEnabled`). With routing off, no call is billed for a decision nobody applies.
  - The thresholds are whole percents from 1 to 100, in place of the rules' 0.75 and 0.8. A percent divided by 100 is the same double as the rules' fraction, so a threshold met exactly still escalates.
  - The switch and the thresholds enter the policy version. The env file does not, since no decision depends on where the key is kept. A deployment that sets none of them keeps the version it had.
- **The key (2b-i)** is `TYPESAFE_API_KEY` in the env file `env_file` names (the user, U8), never an environment variable or an `op://` reference.
  - Load refuses `enabled = true` with no `env_file`. So the issue's "`config resolve` errors when a role uses `jev_complexity` and the key doesn't resolve" holds while Jev is enabled: the coder role always uses it, and otherwise every user would need a key.
  - `config resolve --check-secrets` reads the key whenever `env_file` is set, enabled or not, and reports the file as set or missing, never the key.
  - `jev.Keys` reads the file when asked, never before, so a key changed in the file needs no restart. A key read is kept 10 minutes. At most one read of a file is in flight; it is left to finish however long the file takes, and each ask waits at most 1 s for it. So a locked 1Password costs an ask a second, and its reader one read for as long as it stays locked (two goroutines with the default reader: the read and trail's open), never one per ask.
  - `jev.Asker` asks with that key, and a 401 drops it, so a key rotated in the file is read at the next ask.
  - Routing keeps the default as `jev_key_unavailable`, with `jev_error`, for a caller that had no key (`ErrJevKey`).
  - The endpoint is no setting: no layer can send the key elsewhere.
- **Spawn's call (2b-ii).** `worker spawn` asks Jev once per spawn, through the workforce service's `Jev` (`internal/workforce/jev.go`):
  - after the preflight and routing's decision, and before the workforce lock and anything opens. So a spawn the preflight refuses bills no call, and the wait holds no lock: at most a second for the key and the rules' 2 s for the answer. Whatever refuses a spawn under the lock comes after the ask: the slot cap, the group or repo changed since the preflight, a next id herdr cannot take as an agent name, a failed read of the team or a launch that cannot be planned. A request sent by then is billed for nothing opened, the price of never holding the lock through a call.
  - only for a decision that `AsksJev`, while `Policy.JevEnabled`. It reads the decision, its provider included, never the group, so a per-worker provider (G3) needs no change here.
  - with `JevRequest`'s body, within `JevTimeout`, and the key from `env_file`, its `~/` expanded with the daemon's HOME.
  - No HOME, or no key (`jev.ErrNoKey`), is `ErrJevKey`: the default, as `jev_key_unavailable`, with the failure said once in `jev_error`. A packet `JevRequest` refuses is never sent: `jev_failure`. Only a Go caller can send one that is not UTF-8, since JSON decoding repairs it.
  - `ApplyJev`'s decision is every worker's launch, row and result, and the routed event's. It keeps `route`'s timestamp, from before the ask, so the row's routed time and the event's time are from before it too.
  - A service with no `Jev` asks no one: the decision keeps `jev_disabled`. Only tests build one; the daemon always gives one.
  - `team up` never asks. It has no packet, so its coders' decisions are `task_not_found`.
- **The daemon** gives the service `jev.Asker`, at System One's endpoint, with one `jev.Keys` for the daemon's life. Every op reads the configuration afresh, so switching `[routing.jev]` or moving the env file needs no restart.
- **The event.** `agentisan.worker.routed` gains `agentisan.routing.jev_error`, and daemon.log's routed line carries the whole decision. Neither carries the key.
- **Live, nothing asks yet.** The user's `coder = "claude_strong"` override (U12) names the coder's binding, so no coder decision asks Jev until that override goes, at 2d's calibration.
