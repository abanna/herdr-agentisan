# ADR-001 A62. A worker's provider: a command and a model per provider, and a type's provider a default

*Overrides:* A50's "The provider is the type's agent command" and its "Putting a type on the other provider is a configuration change: its group's `agent.command`", and A23's precedence of a group's agent, review's codex and the top-level command in "The configuration `worker spawn` reads"; and A63's "P16 (A62) widens them to every provider a type may run". *Adds to:* D9, D12, A46 and A50.

Recorded with NERD-5517 (Codex parity P16, rows R7, R14, R15, R37 and R20, part of NERD-5501). It follows the user's decisions of 2026-10-23: Q2 (a), Q3, Q22, and the addendum that Claude and Codex are interchangeable for every type. It also follows the boss's answers to its Stage 3. A50's and A23's text is kept as written.

Built in parts:
- **P16 (this part):** the settings, `Profile.AgentFor(type, provider)` and the checks.
- **P17 (NERD-5518):** the routing overrides per provider.
- **P18 (NERD-5519):** `worker spawn --provider`, the task packet's preference, the row's provider column, and the mixed-group spawn, team up, occupancy and retire tests.

Until P18 a worker runs its type's default provider.

- **The rule.**
  - Every worker runs claude or codex, its provider.
  - A type has a default provider, and a spawn may choose the other (P18).
  - Routing still never changes the provider it is asked for (A50): it routes within the provider the worker runs.
- **The keys,** under the `agent` tables:
  - `[agent.claude]` and `[agent.codex]`: a provider's `command` and `model`, for every type that runs it.
  - `groups.<g>.agent.provider`: the type's default provider, claude or codex.
  - `[groups.<g>.agent.claude]` and `[groups.<g>.agent.codex]`: the type's own command and model for a provider.
  - `agent.command` and `agent.model`, and a group's, keep their meaning: the default agent, whose executable is its provider.
- **The type's default provider** (`Profile.DefaultProvider`) is the first of:
  1. claude, for the debugger;
  2. the group's `provider`;
  3. the provider of the group's own command;
  4. codex, for review;
  5. the provider of the top-level command.
- **The command under a provider** (`Profile.AgentFor`) is the first of:
  1. the group's command for the provider;
  2. the group's own command, when it is the provider's;
  3. for review under codex, the built-in `codex --no-daemon --sandbox read-only` (A55);
  4. the top-level command for the provider;
  5. the top-level command, when it is the provider's;
  6. the provider bare.

  Review's built-in outranks a top-level `[agent.codex]`, as it outranked the top-level command. A codex command written for coders, say one with `--sandbox danger-full-access`, never reaches the reviewer. A59's sandbox goes with every codex launch whose command chooses none, whichever command it is.
- **The model under a provider** is the first of:
  1. the group's model for the provider;
  2. the group's model, when the provider is the type's default;
  3. only when the command is the top level's: the top-level model for the provider, then the top-level model when the top-level command is the provider's.

  So a group's own command, and review's built-in one, run without a top-level model, as before.
  - The debugger keeps its own rule (A32), widened to the new keys: its group's claude model, else its group's model, else the top-level claude model, else the top-level model when the top-level command is claude's.
  - It never runs a top-level command or one of its group's.
- **A profile that sets none of the new keys** resolves every type's command and model as before, under its default provider (`TestAgentFor`). Two things change for keys that already exist:
  - A review group on claude, by its own command, no longer loads (the gaps, below).
  - A launch whose model the other provider runs is refused at spawn, whoever chose the model (below). Examples: a codex group command with `model = "sonnet"`, or `--model sonnet` for a codex group while routing is off. Before, both launched with the model as given.
- **A provider's command is flags only.**
  - herdr's `agent.start` runs its own claude or codex by kind, from the shell's PATH, with arguments only and no environment.
  - So a provider's command names its provider bare, then flags. It has no path, no other program, and no per-worker `CODEX_HOME` or other environment. Codex's `-c key=value` is the only per-worker Codex setting. Anything more is herdr's to add, not the plugin's.
  - Each provider's command is held to D12, the launch-flag check (A53) and, while routing is on, the codex profile refusal (A50).
- **The gaps.** The user's rule is that Claude and Codex are interchangeable for every type. Two refusals remain, each temporary. Each is `ErrProviderRefused`, and its message says it is a gap and names what lifts it:
  - **The debugger runs claude only** until Codex has a read fence like the one the plugin's Claude launch carries (NERD-5530).
    - A codex provider or a codex table in its group is refused.
    - Its group still sets no command (A32).
  - **Review runs codex only** until two things exist: routing v2 (NERD-5529), which lets code_review bind a claude binding, and a read-only Claude review launch.
    - Until then a review group on claude, with routing off, would run the top-level claude, which has no read-only fence (A55). With routing on, the v1 rules block it.
    - A `provider = "claude"`, a claude command or a claude table in the review group is refused.
    - This retires A23's review set back to claude: that configuration no longer loads.

  Load refuses each, whichever key would choose it. `AgentFor` refuses each too, for a profile Load did not build.
- **The boss** is no spawned type and runs claude by default. A Codex boss is NERD-5528 (P15).
- **A model belongs to its provider.** `ModelFamily` names the provider a model's name says runs it, matched without regard to case:
  - **claude:** a `claude-` model, a Bedrock `anthropic.claude-` one with or without its region, or a Claude Code alias (opus, sonnet, haiku, fable, opusplan), with or without `[1m]`;
  - **codex:** a `gpt-`, `codex-` or o-series model;
  - **neither:** any other name, which is never guessed at.

  Where each check runs:
  - `config resolve --project` refuses a model in a table for the other provider (`Profile.CheckModelProviders`). It checks `agent.model` against the top-level command's provider, a provider's table against that provider, and a group's model against the type's default. The error names the key and both providers, never the model.
  - Spawn refuses a launch whose model the other provider runs, whoever chose it, before anything opens.
  - Load does not, so one group's model never stops `team status`, the dashboard or `send`. A50 keeps `CheckRoutingProviders` out of Load for the same reason.
- **A repo file** (A46) may set each provider's model, `agent.<provider>.model` and `groups.<g>.agent.<provider>.model`, as it sets models. It never sets `provider`, which chooses what runs, nor a provider's command.
- **Routing.**
  - While routing is on, every provider's model key is refused as `agent.model` is (A50), and so is a codex profile in a provider's command.
  - `CheckRoutingProviders` checks each (type, provider) pair a spawn runs (A63). Until P18 that is the type's default provider alone, the provider of `AgentFor(type, "")`'s command, since nothing chooses another.
    - Checking every provider a type may run, which A63 expected from this part, would refuse an override of a pair no spawn can reach yet.
    - P18's `--provider` widens the pairs to `providers` less those the type is refused.
- **Later parts.**
  - **P17:** a string override binds only its own binding's provider, and a list sets one binding per provider.
  - **P18:** `worker spawn --provider claude|codex` chooses the provider. With no `--provider`, the task packet's `provider_preference` chooses; with one, it must agree. Each row records the provider its worker runs.
