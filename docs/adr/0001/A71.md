## Context

- **Today.** A43 assumed herdr's integrations were never installed, so a herdr restart would resume no worker and A35 would mark every row lost. On this machine they were installed, with herdr's switch at its default, on. A restart would have relaunched every agent pane as a bare `claude --resume` or `codex resume`, without the flags spawn gave (e7fdd2e8, 2083a5f6). The user set herdr's switch off, so a restart now resumes nothing, and every worker is spawned again by hand.
- **What herdr 0.9.5 offers.** A pane's reporter can attach its own resume command, which herdr runs on restore in place of its own bare one (4d2ac829).
- **Live check 1** proved it with the integrations installed: the command is stored, kept through a stop and replayed, and every flag of a Claude and a Codex launch takes effect.
- **Live check 2** proved the same with the integrations absent. It also found that:
  - a command stored across a start with herdr's switch off stays on a plain shell, where the plugin can no longer release or replace it, and replays at a later start;
  - herdr gives the agent's name back only on the first start after the agent ran;
  - herdr's own sessions outlive an uninstall.
- **The user's decisions,** which this amendment does not reopen:
  - support is built, while herdr's switch stays off;
  - a resumed worker starts with exactly the flags it was launched with;
  - the boss is started by hand for now;
  - the worker's own hooks report its session id;
  - the switch is `[resume] workers` in the plugin's file, with a popup and three actions;
  - the popup may change herdr's own setup after the user confirms it there;
  - the start notice tells each boss which workers came back and which were lost.

## Terms

- **The plugin's switch:** `[resume] workers` in the plugin's shared file (R14).
- **herdr's switch:** `[session] resume_agents_on_restore` in the config file herdr's server reads. herdr reads it only when the server starts (`src/app/mod.rs:439`), and it is on by default (`src/config/model.rs:278`).
- **herdr's integrations:** herdr's Claude and Codex hooks in the user's `~/.claude` and `~/.codex`. Through them herdr records a session (`herdr:claude`, `herdr:codex`) on every pane they run in.
- **A command:** the `resume_argv` the daemon reports on a pane with `pane.report_agent_session`.
- **A record:** the daemon's row in `resume_reports` for a command it may have left with herdr (R7).
- **A verified herdr:** a server whose `ping` answers a version this build was checked against, `0.9.5` today, while the herdr its next start would run answers one too (R22).

## Part 1. What a worker carries

- **R1. Only a restart resumes, and only with the worker's own launch.**
  - A rotation still starts a fresh session that reads the handoff (D7).
  - A herdr start with both switches on resumes each reported worker's own session. herdr runs the command; the plugin writes it.
  - A resume is no rotation: the worker keeps its logical id, its row, its inbox and its context level.
  - *Evidence:*
    - Restore runs a reported command in place of herdr's own plan (`src/persist/restore.rs:824-833`).
    - It types the command into a new shell in the pane's directory, once a client is attached with a non-zero terminal area (`src/app/agent_resume.rs:99-104`, `:226-319`).
    - Live check 1 steps 6 to 9 and live check 2 part A steps 3 to 11 show it stored, kept through a stop, replayed and in effect.

- **R2. The session id comes from the worker's own hooks** (the user's decision): a new pane token, `session`, with `session_at`.
  - **The writers.**
    - `report turn`, under Claude and Codex, sets both on every turn it places, whether or not the turn states an item or a stage. A turn that states neither still sets nothing else (A42).
    - `report codex` sets both in every report, beside `ctx`.
    - A hook inside a subagent, which carries `agent_id`, sets neither (A42).
    - `report statusline` does not write it.
  - **The keys** (the token contract's table, which a new key joins before it ships):

    | Key | Writer | Target | Format | TTL |
    | --- | --- | --- | --- | --- |
    | `session` | `report turn`, `report codex` | Agent pane | The hook payload's `session_id`, only in canonical lowercase UUID form (`8-4-4-4-12` hex); anything else writes nothing | 24 h (A5), set again by every report |
    | `session_at` | `report turn`, `report codex` | Agent pane | Unix milliseconds of the report, canonical decimal, in `ctx_at`'s format (A61); written with `session` | 24 h, with `session` |

    Source `agentisan`, as every report's.
  - **One key.** NERD-5562's planned "thread token" for a Codex boss's wake is this key. It adds no second token.
  - **The daemon takes it into the row only when all of these hold:**
    - the row is bound to the pane in the same poll, and active;
    - herdr detects the row's provider in the pane;
    - `session_at` is no earlier than that agent process's start, A47's start, which the launch-model cache reads (A39);
    - the value differs from the row's.

    A start the poll cannot read yet takes nothing that poll. This is stricter than A61's fallback for `ctx`, since a wrong session would resume the wrong conversation.
    - The write is a compare-and-set on the row as read (A35), and sets `session_id` and `session_at`.
    - An absent or expired token never clears the row's session: tokens die at a restart and after 24 h (A35's table, A5).
    - A later id from the same bound pane replaces it, as after `/clear`.
  - **Spawn passes no `--session-id`.** It never has (`git grep` on `internal/` finds none), and the hooks are the one source for both providers, so the launch recorded is exactly the launch run (R4).
  - **The cost:** a worker never prompted has no session, and goes lost on a restart, as now (R21).
  - **Budget.** An agent pane a team places now carries 16 keys, up from 14: `ctx`, `ctx_at`, `ctx_ok`, `ctx_warn`, `ctx_hot`, `model`, `model_at`, `item`, `stage`, `stage_at`, `stage_now`, `stage_old`, `handoff`, its order key, `session` and `session_at`. `report turn` sets at most 5 keys in one report and `report codex` 6. All are inside herdr's 16 per report and 32 per target.
  - *Evidence:*
    - Codex's hook inputs carry `session_id` on `PostToolUse`, `PostCompact`, `UserPromptSubmit` and `Stop` (codex-rs `hooks/src/schema.rs:324-325`, `:368-369`, `:568-569`, `:589-590`). The `Stop` request's `session_id` is the thread's `ThreadId` (`hooks/src/events/stop.rs:28`), the id `codex resume` takes. Not re-checked.
    - Claude's hook input carries `session_id` among its common fields (Claude Code hooks reference: docs, not run).
    - **Neither id has been seen from the plugin's own hooks.** Live check 1's Claude id came from `--session-id` and herdr's SessionStart hook, and live check 2's Codex id from the rollout file. Slice 1b's live check reads both (Part 7).
    - No hook of the plugin's runs on `SessionStart`, so a worker has a session only from its first prompt (Claude) or its first prompt or tool use (Codex).

- **R3. The row records the launch.** One new migration, numbered at build time; 0011 is the next free number on `e3bd8ad`.
  - **`workers.launch_args`:** the JSON array of the arguments spawn gave `agent.start`, exactly (`internal/workforce/spawn.go:835`).
    - It is written at every bind, by spawn and `team up` alike, as A66's `provider` is. A bind of a retired or lost id writes it afresh.
    - The program is the row's `provider` (A66), which is the launch's kind.
    - **The debugger's is never stored:** its launch carries its role as a prompt, and it is never reported (R21). Its row's `launch_args` stays NULL.
    - The arguments are never logged.
  - **`workers.session_id` and `workers.session_at`:** NULL until R2 takes a session. A new bind clears them.
  - **`handoffs.new_launch_args`:** the replacement's arguments, which NERD-5647's `--replaces` writes when it begins a handoff.
    - A handoff keeps the provider (A66). So `--replaces` launches the replacement under the row's provider, and refuses a launch of the other one before anything opens.
    - Completing a handoff (A33 part 2b-1) moves the arguments onto the row and clears its session, which the replacement's hooks then report.
  - **The table `resume_reports`:** R7's records.
  - A row bound before the migration has no `launch_args`, and nothing is ever reported for it.
  - *Rests on* the user's decision that a resumed worker starts with exactly the flags it was launched with (4ff893a2). The columns follow migrations 0003 and 0008. The arguments are the ones `plan` builds (`internal/workforce/spawn.go:622-700`).

- **R4. The command is the recorded launch, unchanged, behind the resume marker.**
  - **Claude:** `claude --resume <session> <launch_args…>`.
  - **Codex:** `codex resume <session> <launch_args…>`.
  - Nothing is rebuilt from the current configuration (the user's decision). A configuration changed since the spawn does not change a running worker's model, effort, sandbox or hooks across a restart.
  - **Launch flags that would fight the marker** are refused at `config resolve` and at spawn, beside A23's refused flags, with or without an attached value:
    - for a claude command: `--resume`, `-r`, `--continue`, `-c`, `--fork-session`, `--session-id`, `--from-pr`, `--print`, `-p`, `--background` and `--bg` (`claude --help`, 2.1.325);
    - for a codex command: `resume` or `fork` as any argument, `--last` and `--all` (`codex resume --help`, 0.166.0).

    This is a live change for every user from slice 1a, whatever the switches say. No default command carries one of these flags. A row recorded with one anyway is never reported, and `team status` shows its resume as `refused`.
  - **Before it is reported,** the command is checked by herdr's own rules (`src/agent_resume.rs:58-89`):
    - a bare first word;
    - at most 64 arguments and 8,192 bytes;
    - no control character and no apostrophe.

    A command that fails them is never sent. It is logged at warn once, and `team status` shows the row's resume as `refused`.
  - **The flags a resume takes.** `codex resume --help` (0.166.0) lists the same flags as `codex` itself: `-c`, `-m`, `-p`, `-s`, `-a`, `-C`, `--add-dir`, `--search` and `--no-daemon`, among others. `claude --help` (2.1.325) states no conflict with `--resume` for any flag but those refused above.
  - **A limit:** a positional argument in a worker's own command, a prompt, would be sent again on every resume. Spawn adds none to a worker's launch, and the debugger's is never stored (R3).
  - *Evidence:*
    - Live check 1 step 8 and live check 2 part A steps 5, 9 and 10: every flag of both commands was in effect after the resume. Neither check used spawn's actual `--settings` hooks value. Live check 3 does.
    - The bare control came back on Sonnet, not haiku (live check 1, "Where it differed"; live check 2, question 1).
    - The turn hooks' `--settings` value is about 250 bytes and holds no apostrophe (`internal/workforce/spawn.go:549`).

## Part 2. Telling herdr

- **R5. The daemon reports only on a verified herdr, while both switches are on.** Live check 2 forces this: a command stored across a start with herdr's switch off can no longer be released or replaced, and replays at a later start (R10).
  - **The providers it reports.** None until slice 2c-2; claude from slice 2c-2; codex from slice 4. A merged build never reports a provider before it can re-bind, name and tell the boss about a resumed worker of that provider (Part 7).
  - **When.** Each poll, for each row that meets all of these:
    - live, active and bound in this poll;
    - its type is not the debugger;
    - its provider is in the set above;
    - it has `launch_args` with no refused flag, and a `session_id`;
    - herdr detects the row's provider in its pane;
    - no record for that terminal, `pending` or `live`, already holds the same session, the same command and the same agent process start (R7).
  - **The call.** `pane.report_agent_session` with:
    - the pane id that `pane.list` lists with the row's terminal in that poll;
    - source `herdr-agentisan`;
    - the provider as `agent`;
    - the command as `resume_argv`.

    It never sends `agent_session_id` or `seq`, and the daemon never uses `pane.report_agent`.
  - **The record is written first,** as `pending`, before the call (R7).
  - **Answers.**
    - `ok` turns the record `live`.
    - `resume_not_accepted` ends the record, and the call is asked again next poll.
    - `invalid_resume_argv` ends the record. It is logged at warn, and not asked again for that command.
    - Any other failure, a timeout included, leaves the record `pending`: herdr may hold the command. The call is asked again next poll.
  - **`ok` proves little.** herdr answers `ok` and stores nothing for a report without a `seq` on a pane where the same source once sent one (`src/app/api/panes.rs:1613-1615`, `src/terminal/state.rs:1946-1952`). Only this plugin reports under `herdr-agentisan`, and no caller of it sends a `seq`.
  - **herdr's switch is read from the file herdr's server reads:**
    - `HERDR_CONFIG_PATH` from the daemon's own environment (`src/config/io.rs:195-199`);
    - else `$XDG_CONFIG_HOME/herdr/config.toml` (`io.rs:30-35`);
    - else `~/.config/herdr/config.toml` (`io.rs:61-68`).

    The daemon inherits the server's `HERDR_CONFIG_PATH`: `[[startup]]` and the actions both start through `start_plugin_command` (`src/app/api/plugins/runtime.rs:161-199`), which adds the plugin's variables and clears none (`:39-80`, `:126`).
  - **How it reads.** Every poll looks at the file as A36 looks at the shared file: modification time, size and file identity. It reads the file again when any of these changed.
    - **On:** the file is missing, or it parses and leaves the key unset or true.
    - **Off:** it parses and sets the key false.
    - **Unknown:** anything else. herdr loads its defaults, which have the switch on, after a parse error anywhere in the file, a type error in another key included (`io.rs:142-148`, `:172-178`). The daemon's parse cannot see every such error. So on each change it also runs the server's own executable, found from the server's pid as A60 finds a peer, as `herdr config check` with `HERDR_CONFIG_PATH` naming the file. A non-zero exit makes the reading unknown.
    - An unknown reading reports nothing, as off does, and the verdict says `unknown`, or `unsafe` while a bare or stale pane exists (R13). The cost: while `herdr config check` reports any issue, an unknown key included, no worker is reported. The popup and `team status` name the issue. On this machine it exits 0 today (2026-11-17).
  - *Evidence:*
    - The parameters are at `src/api/schema/panes.rs:382-397`. The refusals are at `src/app/api/panes.rs:1611` and `:1687`.
    - herdr accepts the report on a pane where it detects that agent and no other source holds the pane (`src/terminal/state.rs:1931-1942`).
    - Both live checks reported without `agent_session_id`. Live check 2's pane `sd` showed that adding it gains nothing.
    - The switch is read only at start: live check 2, question 2 (T1 to T3).

- **R6. The daemon releases a command while the agent still runs.**
  - **The call.** `pane.release_agent` with the pane id, source `herdr-agentisan` and the agent, and no `seq`.
  - **When.** The record's terminal is listed under that pane id in the same read, herdr detects the record's agent there, and any of these holds:
    - the plugin's switch is off;
    - herdr's switch reads off or unknown;
    - herdr is not verified (R22);
    - the record's row no longer binds that terminal: it was retired or went lost, a handoff completed off it, or it was bound again elsewhere.
  - **On every pane.** A pane that also holds a herdr session is released too. herdr's bare resume of that pane at the next start is shown as `unsafe` (R12, R13), which the popup and the boss's notice name.
  - **The answer proves nothing.** herdr answers `ok` whether or not it forgot the command (`src/app/api/panes.rs:1890-1910`), and nothing reads a command back: `pane.list` and `session.snapshot` carry no `agent_resume` (`src/api/schema/panes.rs:449-484`). So the record ends only when the call was made under the conditions above. A release herdr could not apply leaves the record as it was.
  - **Turning either switch off** releases every record at the next poll. The popup's herdr `off` releases every one before it writes the file (R16).
  - *Evidence:*
    - Release on a running Claude kept its process, its detection and its name, and cleared the command (live check 2 part A step 13; `src/terminal/state.rs:1811-1866`).
    - herdr forgets a command by source and agent, not by terminal (`src/terminal/state.rs:2022-2029`). Hence the same-read terminal check: a reissued pane id would otherwise lose another worker's command.
    - Release on a running Codex was never tried. It is slice 4's gate.

- **R7. A durable record of each command, in `state.db`.** The table `resume_reports` keeps one record per report:
  - its pane id, the terminal it was reported on, and that pane's shell pid and start (A35);
  - the pid and start of the agent process it was reported for (A47's start, which R2 reads);
  - its row's logical id and generation;
  - the provider, the session, and a SHA-256 of the command;
  - its state, `pending`, `live`, `stale` or `ended`, with the times it was written and changed.

  A record means "herdr may hold this command". `pending` and `live` count alike everywhere but in R5's answers and R12's bare set. A record ends only on evidence that herdr no longer holds the command:
  - the release of R6;
  - **within one herdr run,** while a poll still lists the record's terminal: no process with the record's pid and start lives, and herdr detects no agent of that provider in the pane. A worker suspended with ctrl-z still lives, and herdr keeps its command (A35), so its record stays. herdr clears the command on that exit, unless the same source reported again after it (`src/terminal/state.rs:375-385`, `:550-569`), which R5 never does on a pane with no agent;
  - the pane closed: its terminal and its pane id both listed nowhere in a poll whose `pane.list` answered;
  - herdr detecting another agent kind in the pane, or another source holding it, either of which drops the command (`src/terminal/state.rs:1995-2009`);
  - the daemon closing the pane (R11);
  - R5's two definite refusals.

  **One command per pane.** herdr keeps one reported command per pane, and a new one replaces the old (`src/terminal/state.rs:1931-1952`). So when a newer record for the same pane turns `live`, the older ends. While the newer is `pending`, both count, and R8's proof accepts either's command.

  **Across a restart,** when the record's terminal is listed nowhere and its pane id still is, the record belongs to R8 and R10. The exit rule never ends it then. After a start with herdr's switch off, the pane is a plain shell with no agent, and herdr still holds the command (live check 2, parts B and C).

  A record kept too long costs a false stale entry, which a close clears. A record dropped too soon would hide a replay. The poll's writes to records are compare-and-sets, as A35's are on rows. The daemon is their only writer (D3).

- **R22. herdr's version, and upgrades** (new in revision 2).
  - **The gate.** The daemon reads herdr's version from `ping` (`herdr.Pong.Version`), which it already asks every poll (A3). A4's protocol pin cannot tell 0.9.3 from 0.9.5: both speak protocol 22 (`src/protocol/wire.rs:20`; `internal/daemon/daemon.go:27`). A herdr is verified when its version string is in this build's list for resume, `0.9.5` today. The match is exact: a preview build answers `0.9.5-preview.<id>` (`src/build_info.rs:13-21`), and is not verified. `HERDR_AGENTISAN_ALLOW_UNVERIFIED` (A4) does not open the gate.
  - **The herdr that starts next.** A server's binary can change under it: an installer such as mise moves `latest` to a newer version while the server runs, and the next start runs that one. So the daemon also finds `herdr` on its own `PATH`, which it inherits from the server (`src/app/api/plugins/runtime.rs:39-80`), and reads its version with `herdr --version`. It reads it again when that file's modification time, size or identity changes, as A36 looks at the shared file. `HERDR_BIN_PATH` names the running binary, not the next, so it is not used. A next herdr whose version is not in the list, or that cannot be run or read, leaves the server unverified until it is the running one and verified.
  - **On any other version:**
    - the verdict is `unsupported` (R13);
    - nothing is reported (R5);
    - R6 releases every record while its agent runs;
    - the popup refuses herdr's `on` (R16).
  - **What keeps running:** R8 to R11, R17 and R18. After an upgrade, the new herdr has already replayed whatever it held. Stopping the re-bind would leave resumed workers unbound while the boss is told to spawn them again.
  - **What the gate cannot stop.** A command reported under 0.9.5 is replayed by whichever herdr starts next, under that herdr's rules. Restore checks each stored command against its own argv rules and drops one it rejects. The pane then falls back to herdr's bare plan where it holds a herdr session (`src/persist/restore.rs:865-869`, `:824-833`).
    - So an upgrade the daemon can see, a new `herdr` on the server's `PATH`, releases every command before the next start, with no step from the user. One it cannot see, a herdr started from another path, still needs the user: before upgrading, turn the plugin's switch off and wait one poll, about 3 s. The popup and `team status` say both.
  - **`herdr update --handoff`** (a live handoff):
    - herdr hands each pane's process over, and keeps its stored command, its name and its pane id on a new terminal (`src/persist/restore.rs:581-591`, `:686-712`). A35's shell proof re-keys the row, and its record follows.
    - A pane whose process herdr could not hand over is restored as at a start, but with herdr's switch taken as on, whatever the file says: `restore_handoff` passes `true` (`src/persist/restore.rs:96-113`, `:196`).
    - So a live handoff can replay a command, or bare-resume a herdr session, while herdr's switch is off.
    - Live check 3 runs a live handoff with a stored command on a scratch server.

## Part 3. After a restart

- **R8. A reported worker is re-bound by its resume** (amends A35's reconcile). This applies to a row that is not lost, whose terminal herdr lists nowhere, that has a shell, and that has a `pending` or `live` record. It runs whatever the switches say now: a command already stored replays whatever they say today.
  - **The candidates are A35's, in A35's order.** For each:
    - **Shell proof.** The candidate holds the row's shell: a herdr live handoff. The row re-keys as today, and the record follows it.
    - **Resume proof.** A foreground process of the candidate (`pane.process_info`, A39) proves the row when both hold:
      - its executable's basename is the record's provider;
      - its arguments end with the record's command after its first word, element for element: the marker (`--resume <session>` for claude, `resume <session>` for codex), then the recorded `launch_args`, to the last argument. The SHA-256 of the basename followed by that tail is the record's.

      Arguments before the marker are allowed. herdr types the command into the user's shell (`src/app/agent_resume.rs:226-319`), so an alias or a shell function may add flags of its own first, as it did at the spawn. A bare resume of the same session fails it: herdr's own plan, or one typed by hand, ends at the session, and spawn never records a launch with no arguments (claude gets `--name`, codex `--no-daemon`). herdr reads `/proc/<pid>/cmdline` whole (`src/platform/linux.rs:764`). The proof is against the command the record says herdr holds, not the row's latest session: after a `/clear` the two differ until the next report lands.

      The row then re-keys to the candidate's pane and terminal. Its shell is cleared for the poll to read, as `CompleteHandoff` does (A35), and its session becomes the record's. The record re-keys with it, with the new agent process's start.
    - **No shell yet.** A candidate with no shell leaves the row unverified, with no limit, as today (`internal/daemon/bind.go:203`). herdr gives a replaying pane no shell until a client attaches, and shows it as the agent at rest meanwhile (`src/persist/restore.rs:592-625`).
    - **A shell, but neither proof.** The row stays unverified until 20 polls (about 60 s, A44's grace for a new agent) after the poll that first saw that candidate's shell. It is then judged as A35 says: another shell, and lost when no candidate remains. herdr spaces the replays by `startup_per_agent_delay_ms`, 100 ms by default (`src/config/model.rs:279`).
  - A row with no `pending` or `live` record is judged as A35 says, unchanged.
  - The arguments are matched in memory and never logged (A39). A process whose arguments herdr cannot read gives no proof.
  - *Evidence:*
    - The first argument is a full path for Claude (`…/claude`) and a bare `codex` for Codex, so the provider is matched by basename (live check 1, "The re-bind proof works").
    - Both forms were read at the restored pane id, on a new terminal, in both live checks.

- **R9. A re-bound worker gets its name back** (the daemon never relies on herdr's name restore).
  - **Why.** herdr restores an agent's name only on a pane it replays from a plan, and only for an agent `agent.start` launched (`src/persist/restore.rs:605-611`). A start with herdr's switch off drops every name (`:705-712`), and a later replay comes back unnamed (live check 2, question 2, T3). Both live checks got the names back on an ordinary replay, so this is rare while R5 and R6 hold.
  - **[Q5] The call.** After R8's resume proof, when `agent.list` names the pane's agent other than the logical id, the daemon calls `agent.rename` with the pane id and the logical id (`src/app/agents.rs:90-135`).
  - **Its refusals:**
    - the pane shows no agent yet, or herdr still has a launch pending (`:124-129`): asked again next poll;
    - the name is another agent's (`:104-112`): logged at warn, with a start line (R17). The row stays bound, and its messages wait. A30's dispatcher prompts only a bound pane whose agent has the worker's name (`internal/daemon/messages.go:232`).
  - A name given this way is no managed agent's (`set_agent_name`), so herdr does not restore it at the next restart either. R8 and R9 run again then.
  - herdr can erase such a name when one of its own hooks reports another session on the pane (`reconcile_agent_name_owner`, `src/terminal/state.rs:2366-2377`). That needs herdr's integrations installed, which R13 already shows as `unsafe`.
  - Never run on a replayed pane. Live check 3 runs it.

- **R10. Stale commands.** A stale command is one stored on a pane where no agent of the plugin's runs.
  - **How one arises.** A start with herdr's switch off gives each reported pane a fresh shell and keeps its command (`src/persist/restore.rs:699-703`). From then on:
    - the plugin's release does nothing there, since no agent of that kind runs (`src/terminal/state.rs:1823-1827`);
    - a new report is refused (`:1933-1942`).

    At the next start with herdr's switch on, herdr replays it, however many starts later. The replay displaces whatever was started in that pane since, unnamed and bound to no row (live check 2, parts B and C).
  - **The ways out** are closing the pane (R11), or starting an agent of that kind in it and releasing it while it runs (live check 2, pane `sa`). The daemon starts no agent for this (I5).
  - **R5 and R6 prevent nearly all of them,** since nothing stays reported while herdr's switch is off. What is left:
    - a restart between herdr's switch going off in the file and the daemon's next poll;
    - a restart while the daemon is down;
    - a replay that failed;
    - an agent the daemon could not release;
    - a live handoff's pane that herdr could not hand over (R22).
  - **Detection.** After a restart, a `pending` or `live` record whose row did not re-bind turns `stale` once R8's 20-poll wait ends while herdr detects no agent of the plugin's in its pane. A pane whose agent is of the same kind but carries no resume proof counts too: live check 2's `se`. The record then re-keys to the pane's new terminal.
  - **It follows its pane:**
    - by terminal while one is listed;
    - by pane id across a further restart, since a restart keeps pane ids (A35's table).
  - **A stale replay.** At a start with herdr's switch on, a stale record whose pane then shows R8's resume proof is a replay. The record turns `live` again, bound to no row, so R6 releases it at once. The start lines (R17) name the pane: it runs an old session of that worker and binds nothing.
  - **Never reused.** No launch path opens an agent in an existing pane: spawn and `team up` open a tab each (A23). The popup and the start lines tell the user and the boss to start nothing in a listed pane.

- **R11. Closing a stale pane** (amends A35 and A23).
  - **Who asks.**
    - The boss: `worker retire <id>`, and a spawn that binds a retired or lost id again, close that id's stale panes.
    - The user: the popup's `c` closes every listed stale pane, after the user types `close` and Enter. That is the plugin's own herdr call, not a change to herdr's setup, so R16's exception is not needed for it.
  - **The close.** For each stale record, under the workforce lock, the daemon closes its pane once both hold:
    - `pane.get` shows the record's terminal;
    - herdr detects no agent there.

    The record then ends.
  - **What it rests on.** The proof is the record, a pane id and a terminal herdr listed in the same read, not the row, which proves no pane while lost (A35).
  - **When it cannot close.** A pane running an agent now, or showing another terminal, is not closed. The answer says why, in `stale_pane: {pane_id, closed, reason}`.
  - **The daemon never closes one on its own.** A stale pane runs no agent, so D1 and I5 do not forbid it, but it is a plain shell the user may have started using.
  - A pane closed is not restored (live check 2, pane `sf`).

## Part 4. Whether the next start is safe

- **R12. The bare set:** panes that would come back as a bare `claude --resume` or `codex resume`, without the flags spawn gave.
  - **Which panes.** Every pane whose `pane.list` entry carries an `agent_session` from herdr's own sources (`herdr:claude`, `herdr:codex`), unless the plugin holds a `live` record for it. A `pending` record does not count: herdr may have refused or never stored that report. A plain shell counts:
    - `pane.list` serves the session the terminal still holds (`src/app/creation.rs:416-439`);
    - a start with herdr's switch off restores it onto a fresh shell (`src/persist/restore.rs:700`).
  - **A pane the plugin reports is not bare,** though herdr still lists its session there: the reported command wins (`src/persist/restore.rs:824-833`; live check 2, pane `rc-relh`).
  - **What empties it.** Only the agent leaving the pane (`/exit` clears the session, the name and the detection: live check 2, `rc-exit`), or the pane closing.
    - herdr drops a release under its own sources and still answers ok (`src/app/actions.rs:1610`).
    - Uninstalling an integration removes its hook file and its entries in `~/.claude/settings.json` or `~/.codex/hooks.json`, and touches no pane's session (`src/app/api/integrations.rs:53-72`, `src/integration/targets.rs:575-615`; live check 2, question 1).
    - So turning herdr's switch on needs every Claude and Codex agent started while the integrations were installed to be restarted once, the bosses and the agents started by hand included.
  - **A replay keeps a pane bare.** A pane herdr bare-resumed holds its herdr session after the resume (live check 2, `rc-bare`).
  - **What uninstalling costs, on the whole machine.** Without herdr's hooks, herdr reads every Claude and Codex agent's status from its screen. That covers every team's agents, the agentisan-skills team's `as-*` and the bosses included, not only this plugin's workers. A finished turn reads `done`, not `idle`, and `herdr agent wait --until idle` times out (live check 2). The plugin is unaffected (R19). The popup says this before the user types `uninstall` (R16).
  - **It is read every poll** from the `pane.list` the poll already makes, server-wide, since herdr's switch is.

- **R13. The verdict.** The daemon judges the server every poll from:
  - whether herdr is verified (R22);
  - the plugin's switch;
  - herdr's switch as the file says (R5), which is what the next start reads;
  - the bare set (R12);
  - the stale set: the records in state `stale` (R10).

  | herdr | herdr's switch | Bare set or stale set | The plugin's switch | At the next herdr start | Verdict |
  | --- | --- | --- | --- | --- | --- |
  | Not verified, or the next herdr not verified | any | any | any | Nothing new is reported, and R6 released the rest. Bare and stale panes replay as the rows below say | `unsupported` |
  | Verified | on | both empty | on | Reported workers resume in full and re-bind; every other pane comes back a plain shell | `ready` |
  | Verified | on | both empty | off | Every pane comes back a plain shell: R6 released the commands | `plugin-off` |
  | Verified | unknown | both empty | any | Nothing is reported, and R6 released the rest, so nothing of the plugin's resumes, though herdr may start with its switch on. `herdr config check` names the issue | `unknown` |
  | Verified | on or unknown | either not empty | any | Bare panes resume without their flags. Stale panes replay an old worker's session over whatever runs there, unnamed and bound to no row | `unsafe` |
  | Verified | off | any | any | Nothing resumes at a start. Nothing stays reported (R5, R6). Bare sessions and stale commands wait for a later start with herdr's switch on, or a live handoff's pane herdr could not hand over (R22) | `off` |

  - **herdr's integrations beside the verdict.** The integrations (`integration.list`, `src/app/api/integrations.rs:10-30`) are shown per provider: not installed, current or outdated. While one is installed, the bare set can grow at any moment. herdr's Settings → integrations installs both at once on one Enter (bd98761d).
  - `integration.list` is read at the GitHub collector's 60 s cadence, and whenever the popup or an action asks.
  - *Rests on* R10, R12 and herdr's restore order (`src/persist/restore.rs:824-833`), and on the user's answer that turning herdr's resume on is refused while any pane would still come back bare (6aba5e0c, answer 2).

## Part 5. The switches

- **R14. The plugin's switch: `[resume] workers = "off" | "on"`,** default `off`.
  - **Where it lives.**
    - Only in the shared `herdr-agentisan.toml`: it is global, since herdr's switch and integrations are per server and per user, and one daemon serves every team.
    - A project's table that sets it is refused. So is a repo file: it is not in A46's `repoFileKeys`.
    - `config resolve` shows it with its layer. `--set` shows there, but the daemon reads only the file.
  - **Read again on a change,** as A36's descriptions are: each poll looks at the file, and reads the key when the file changed. No restart is needed.
  - **On** means "report the providers this build supports" (R5); `team status` names them.
  - **Its writers:** the user by hand, the two actions that set it, and the popup's `w`.
    - Each write changes one line: `workers = …` inside `[resume]`, or a `[resume]` table appended at the end. Comments and every other byte stay as they were.
    - The edited copy must load with `config resolve`'s loader, or nothing is written. It replaces the file through a temporary file and a rename, keeping the file's mode.
    - A key written any other way, such as a dotted key or an inline table, is refused with "edit it by hand". Nothing is written then.
  - This is the first time the plugin writes the file the user edits by hand (the user's decision, 6aba5e0c).
  - *Rests on* the user's answer 1 (6aba5e0c): the setting lives in the toml, not in `state.db`, defaults to off, and is read again when the file changes, as A36 reads descriptions.

- **R15. The surfaces.** herdr 0.9.5 has no plugin menu or plugin settings (bd98761d, Part 1).
  - **Three actions,** with fixed titles:
    - `resume-on`, "Agentisan: worker resume on";
    - `resume-off`, "Agentisan: worker resume off";
    - `resume-status`, "Agentisan: resume status".

    The first two write the plugin's switch, then show a toast stating both switches, the integrations and the verdict. The third opens the popup.
    - **When the toast is not shown, the popup opens instead.** `notification.show`'s answer does not say: with a client attached, herdr answers `shown` even while `[ui.toast] delivery` is `off`, its default, and the client drops the toast (`src/server/headless/notifications.rs:244-289`, `src/config/model.rs:1249-1253`). So the actions read `[ui.toast]` from herdr's file (R5): `delivery`, else the legacy `enabled` (true is `herdr`), else `off` (`src/config/model.rs:1284-1297`). They open the popup unless the delivery is `herdr`, `terminal` or `system`.
    - The actions change the plugin's switch only. Any agent can invoke an action (`herdr plugin action invoke`), so an action proves nothing about who asked.
  - **The popup:** a `[[panes]]` entry `resume`, placement `popup`, running `bin/herdr-agentisan resume popup`.
    - **Opened by** a key line in `docs/config/herdr-keys.example.toml` (`prefix+u`, which herdr 0.9.5 binds to nothing by default), and by a `[ resume ]` button in the dashboard's header, beside `[ btop ]`.
    - **The header** also shows the verdict as a badge, from a new optional snapshot key, `resume`. Its values are a closed set: `ready`, `plugin-off`, `unknown`, `unsafe`, `off`, `unsupported`. A18's contract stays v1, as A68's key did.
    - **It shows:**
      - both switches, with the path of herdr's file and, for an unknown reading, why;
      - herdr's version, the version of the herdr its next start would run, and whether each is verified;
      - the integrations per provider;
      - the verdict;
      - the bare set: each pane, its agent's name or pane id, and its team, with "restart this agent once, or close the pane";
      - the stale set: each pane and the worker it belongs to, with "start nothing in it";
      - the rule for upgrading herdr (R22).
    - **Its keys:**
      - `w` turns the plugin's switch on or off;
      - `c` closes the stale panes (R11);
      - `h` changes herdr's setup (R16);
      - `q` closes.
    - The popup takes no path from its own environment: a caller of `plugin.pane.open` passes its own `env` to the popup it opens (`src/app/api/plugins/panes.rs:356-369`). It asks the daemon, which resolves every path itself (R5).

- **R16. herdr's setup, from the popup only: the exception to A43** (the user's decision, 6aba5e0c).
  - **What may change.** The plugin may change herdr's switch and integrations only through the popup's `h`. Nowhere else may it: no action, no daemon poll, no other command, no op an agent's command calls.
  - **The steps.** `h` offers two.
    1. `uninstall`: uninstall herdr's Claude and Codex integrations that `integration.list` shows installed, through herdr's own `integration.uninstall`, which herdr runs in its server's environment. The popup first states R12's cost to every agent on the machine.
    2. herdr's switch `on` or `off`:
       - `on` is refused while the bare set or the stale set is not empty, while herdr is not verified, or while herdr's file reads unknown. The refusal lists why.
       - `off` has no gate. It first releases every record (R6), so nothing goes stale at the next start.
  - **[Q7] The confirmation.** `uninstall` and `on` each need their word typed, then Enter; `off` needs one key, then Enter.
  - **The write.** One line, `resume_agents_on_restore = true|false`, written:
    - inside `[session]`;
    - or added to an existing `[session]`;
    - or in a `[session]` table appended at the end.

    A key written any other way is refused with "edit it by hand". Then:
    - a dated backup is kept beside the file;
    - the server's `herdr config check`, with `HERDR_CONFIG_PATH` naming the edited copy, must exit 0;
    - the copy replaces the file by a rename, keeping its mode;
    - the write is refused if the file changed since it was read, since herdr's own settings screen writes the same file.
  - **Nothing is reloaded or restarted** (I7). herdr reads its switch only at its next start (`src/app/mod.rs:439`), and the popup says so.
  - **The confirmation proves nothing about who typed it.** herdr 0.9.5 offers no confirmation that an agent on this machine, running as the user, cannot give in the user's place:
    - `plugin.pane.open` checks no caller, and takes the caller's placement, `popup` included (`src/app/api/plugins/mod.rs:491`; the CLI's `--placement popup`, `src/cli/plugin.rs:872`). So any agent can open the real popup as a popup.
    - `herdr terminal attach <id> [--takeover]` reaches any terminal herdr holds by its id, the popup's included (`src/server/headless.rs:1094-1101`, `:1737-1800`; `src/app/popup.rs:161`). Ids are `term_<micros><counter>` (`src/terminal/id.rs:16-22`).
    - Any process of the user's can connect a whole herdr client to the server's socket, and type into whatever the popup shows. herdr serves several clients at once (`src/server/clients.rs:471-479`). Both live checks drove such a client through a FIFO.
    - The agent needs none of these: it can edit herdr's file, or run `herdr integration uninstall`, itself.

    Only something an agent does not hold could prove the user, such as the user's password, a hardware key, or a daemon under another uid. herdr offers none of these, and this amendment adds none.
  - **What it promises instead.**
    - **No path by accident or by the plugin's own commands.** No action, op or CLI command but the popup's changes herdr's setup. The daemon's `resume.herdr` op names only the step, and the daemon resolves every path itself. It refuses (`not_allowed`) unless the caller, placed by its peer credentials (A60's `SO_PEERCRED`, `LOCAL_PEERPID`), is a direct child of herdr's server, runs the plugin's binary by its executable with the popup's subcommand, and is no process of any pane `pane.list` lists. That stops a stray CLI call or a confused agent. It is no proof: another plugin's process, or an agent that opens the popup and types into it, passes it.
    - **Every change is seen.** Each change is logged at warn in `daemon.log`, sent as a workflow event, and kept as a dated backup. Whoever made a change, the daemon reads herdr's file and the integrations every poll (R5, R13): a change shows in the verdict, the popup, `team status` and the dashboard's badge.
    - **No power an agent lacks.** The popup does nothing an agent running as the user could not already do by hand.
  - **Policy, not a boundary,** as A60 says of the board.
  - **What it changes in A43.** "herdr's own integrations are never installed" stays the target, and the plugin no longer assumes it: R12 and R13 check it every poll, and this popup may make it true. "The plugin never writes it" holds everywhere but here.

## Part 6. What the boss and the user are told

- **R17. The notices** (adds to A44).
  - **The start lines.** A44's `started` line goes on the first poll, as now. The poll then appends one line per awaiting row as it settles: `store.Notify` appends to the boss's notice while it is still queued (A44). The boss is started by hand after the restart, so it reads them together.
    - There is no fixed wait: a headless server settles nothing until a client attaches.
    - **Kind `resumed`,** which `notices.skip` can name:
      - `ha-coder-1 came back by herdr's resume (pane w1:p4); it is idle at its prompt: ask it where it stands`;
      - `pane w1:p11 replayed an old session of ha-coder-4 and binds no worker`;
      - `ha-coder-5 came back but cannot take its name (<reason>); its messages wait`.
    - **Kind `resume_lost`,** which `notices.skip` refuses, as it refuses `ctx_ceiling`, since the user decided the boss is told who was lost:
      - `ha-qa-2 was not resumed and is lost; spawn it again or retire it`;
      - `ha-coder-3's old resume command is still in pane w1:p9, which runs nothing; retire or spawn ha-coder-3 to close it`;
      - `ha-coder-6's rotation to pane w1:p12 cannot complete after the restart; worker retire w1:p12 abandons it and releases its messages`. **[Q6]** It is told when R18's match holds.
  - **Kind `resume_unsafe`,** which `notices.skip` can name.
    - Each boss is told once when the verdict turns `unsafe`, `unsupported` or `unknown`, naming the sets' sizes, the version or herdr's file, and the popup's key. It is told again only after the verdict has changed.
    - The user also gets a toast, under R15's rule for toasts. One herdr does not show is logged.
  - The daemon never prompts a resumed worker (D1). The boss decides.
  - *Rests on:*
    - the user's answer that the start notice tells each boss who came back and who was lost, and the boss asks each resumed worker (6aba5e0c, answer 4);
    - A44's append to a notice still queued (`store.Notify`);
    - A33's toast for the ceiling.

- **R18. A rotation pending across a restart** (A33's handoff).
  - **[Q6]** The boss ends it. A33's startup rule stands: the daemon neither completes nor fails a pending handoff.
  - The replacement's pane binds no row, so nothing is reported for it. It comes back a plain shell, unnamed: herdr restores no name on a pane it does not replay (`src/persist/restore.rs:709`). So A33's acknowledgement answers `handoff_changed` and can never complete.
  - The old worker re-binds by R8 like any row; A35 never marks a row with a pending handoff lost. It keeps the role.
  - **When R17 tells it.** It uses A33's own match for the replacement:
    - the handoff's recorded terminal is listed nowhere;
    - the pane at its recorded pane id is gone, or, once R8's wait for that pane has ended, hosts no agent named `<id>-next` or the worker's id.

    After a herdr live handoff, the replacement keeps its agent and its name, so A33's acknowledgement can still complete it, and nothing is told.
  - `worker retire <replacement pane>` abandons the handoff (A33 part 2a), which releases the worker's held messages. The dispatcher delivers them once R9 has named the worker.
  - **Completing a handoff** (A33 part 2b-1) also releases the old pane's command while its agent runs (R6), after the rows move. A restart before `worker retire <old pane>` then replays nothing there.

- **R19. What a resumed worker is.**
  - **Mid-turn.** Its process died with the server, so its turn was cut. What its tools wrote stays, and its pane tokens are gone (A35's table). It comes back idle at its prompt, and R17 tells the boss.
  - **Messages** wait in the inbox while the row is unverified or lost (A35), and are delivered by name once R8 and R9 are done. A message typed as the server died fails and is not retried (A30).
  - **`ctx`, `model`, `item`, `stage` and `session`** return with the agent's next report. For Codex, `ctx` returns after the first resumed turn (both live checks).
  - **The tab's environment** is not restored: herdr restores only its pane identity variables (`src/persist/restore.rs:572-580`). After R8 the pane is bound, so `send`, `handoff ready` and `handoff ack` place the caller by its pane (A64), and `HERDR_AGENTISAN_WORKER` stays the fallback it is. A resumed Codex passes `CheckCodexHost`: `isCodex` reads its parent's `codex resume …` by its first word (`internal/report/codex.go:166`). Live check 3 proves `send` from a resumed worker.
  - **herdr's status without its hooks.** A finished turn reads `done`, an unseen `idle` (`src/app/api_helpers.rs:101`). Spawn's readiness accepts both (`internal/workforce/spawn.go:925`), and so does the team model (`internal/team/idle.go:46`). A44's turn end still comes from `completion_seq`, which herdr sets on a completing state change (`src/app/actions.rs:1755-1761`).

- **R20. `team status` and the snapshot** (adds to A23 and A18).
  - **Each member and each unbound row gains `resume`:**
    - `reported`: a `live` record holds its command;
    - `pending`: no session yet, or its report is not yet answered;
    - `off`: a switch is off, or herdr's file reads unknown;
    - `unsupported`: herdr is not verified, or its provider is not yet in R5's set;
    - `awaiting`: after a restart, waiting for R8;
    - `refused`: R4's checks failed;
    - `none`: no recorded launch, as before the migration, or a debugger.
  - **The team's answer gains `resume`:**
    - both switches, with the reason for an unknown reading;
    - herdr's version, the version of the herdr its next start would run, and whether each is verified;
    - the integrations per provider;
    - the verdict;
    - the sizes of the bare and stale sets.

    The popup lists the sets themselves.
  - **The snapshot's optional `resume` key** carries the verdict for the dashboard's badge (R15).
  - *Rests on* R4 to R13 and R22. A68 is the precedent for an optional, additive snapshot key under contract v1.

- **R21. Out of scope:**
  - a resumed boss, which is a later slice of its own (the user's decision; it has no row, and A47 already reads its agent process);
  - the debugger: its launch passes its role as a prompt, and its read fence's environment is not restored;
  - a replacement pane before its handoff completes;
  - a worker with no session yet, which goes lost on a restart, as now;
  - rows from before the migration;
  - re-prompting a resumed worker;
  - a per-pane opt-out, which herdr lacks;
  - agents other than claude and codex;
  - A33's ceiling toast, which trusts `notification.show`'s answer as R15 no longer does. That is its own issue.
